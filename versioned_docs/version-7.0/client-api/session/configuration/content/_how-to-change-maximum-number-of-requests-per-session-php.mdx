<Panel heading="Request limit">

By default, the limit on the number of requests that a session can send to the server is **30**.  
A session that has reached this limit throws an exception instead of sending any further request to the server.

The limit serves as an early warning of a session that sends too many requests to the server.  
A session represents a single [unit of work](../../../../client-api/session/what-is-a-session-and-how-does-it-work.mdx#unit-of-work-pattern) (e.g., handling one web request).  
Since each request is a remote call to the server, keep the number of requests per session as low as possible.  
e.g., to load multiple documents, use **a single `load` call** rather than **one call per document**

Reaching the limit may indicate a [Select N+1 problem](../../../../client-api/session/what-is-a-session-and-how-does-it-work.mdx#the-select-n1-problem), or a session that you keep open
across several units of work (e.g., a single session that processes all the items of a batch job).

If a single unit of work does need more requests than the limit allows, you can raise the limit
[for a single session](../../../../client-api/session/configuration/how-to-change-maximum-number-of-requests-per-session.mdx#single-session) or [for all sessions](../../../../client-api/session/configuration/how-to-change-maximum-number-of-requests-per-session.mdx#all-sessions).

</Panel>

<Panel heading="Short-lived vs long-lived sessions">

Opening a session is inexpensive.  
When you open a session, the client sends no request to the server, and the new session reuses the document store's
connections to the server and HTTP cache.

The cost of a long-lived session, on the other hand, grows with the number of documents the session tracks.  
By default, a session tracks every document it loads or receives from queries, and keeps these documents in memory.  
Each time you call `saveChanges`, the session checks all the tracked documents for changes, so each `saveChanges` call
takes longer as the number of tracked documents grows.

To handle a series of independent operations (e.g., processing the items of a batch job), it is therefore best to open
a separate session for each operation rather than a single long-lived session for the whole series.

</Panel>

<Panel heading="Single session">

To change the request limit for a **single** session, call the session's `advanced()->setMaxNumberOfRequestsPerSession` method.  
The new limit applies only to this session.

```php
$session->advanced()->setMaxNumberOfRequestsPerSession(50);
```

</Panel>

<Panel heading="All sessions">

To change the request limit for **all** the sessions of a document store, set the store's
`maxNumberOfRequestsPerSession` convention.

<Admonition type="note" title="">

Set this convention **before** calling the store's `initialize` method to start using the store.  
Setting a convention after calling `initialize` throws an exception.

</Admonition>

```php
$store = new DocumentStore();

// Set the convention before calling initialize
$store->getConventions()->setMaxNumberOfRequestsPerSession(100);

$store->initialize();
```
<br />

<Admonition type="info" title="">

The server can also set the limit for all sessions, server-wide or per database, using the client configuration it sends
to clients.  
A limit set by the server overrides the store's `maxNumberOfRequestsPerSession` convention.  
See [Client Configuration (server-wide)](../../../../studio/server/client-configuration.mdx) and
[Client Configuration (for database)](../../../../studio/database/settings/client-configuration-per-database.mdx)

</Admonition>

</Panel>

<Admonition type="note" title="">

* A **subscription worker** is the client-side component that consumes a subscription.  

* The worker connects to the server, receives a batch of documents, hands the batch to your processing code, and
  when done, acknowledges its progress to the server so the server can keep track and provide the next batch.  

* This page explains how to create and run a subscription worker using the client API.

<Panel heading="Creating a subscription worker">

Create a worker using the store's `Subscriptions.GetSubscriptionWorker` method, passing either the
subscription name or a [SubscriptionWorkerOptions](../../data-subscriptions/consuming-subscription.mdx#classes) object.

```csharp
subscriptionWorker = store.Subscriptions.GetSubscriptionWorker<Order>(subscriptionName);
```

<br />

This constructs the worker but does not run it yet.

</Panel>

<Panel heading="Running the worker">

To start processing the documents the server sends, call the worker's `Run` method, passing the
logic that handles each batch:

```csharp
subscriptionRuntimeTask = subscriptionWorker.Run(batch =>
{
    // your batch-processing logic here
});
```

<br />

From this point on, the worker receives and processes document batches, acknowledging each batch 
so the server can keep track of the subscription's progress and provide the next batch if available.  

The `Run` method returns a task that stays alive while the worker is processing. If processing is aborted,
this task completes with an exception.

</Panel>

<Panel heading="At-least-once delivery">

The server advances a subscription's progress only when the worker acknowledges a batch.  
If a worker stops (or its connection fails) before acknowledging a batch, the server will re-send the
same batch the next time a worker connects to the subscription.

Delivery is therefore at-least-once: documents may be processed more than once, but none are skipped.
Make your processing idempotent to make sure that reprocessing a document has no unintended effect.

[Concurrent subscriptions](../../data-subscriptions/concurrent-subscriptions.mdx#connection-failure-and-reassignment)
add another way a document can be reprocessed, by reassigning a dropped worker's documents to the
other workers.

</Panel>

<Panel heading="Worker strategies">

A worker is configured with a strategy, set in the 
[SubscriptionWorkerOptions](../../data-subscriptions/consuming-subscription.mdx#classes) 
`Strategy` property, that decides whether the worker may connect to the subscription 
and how it behaves toward a worker that is already connected.

The following strategies allow only one worker connected at a time:

* **`OpenIfFree`**  
  The server lets the worker connect only if no other worker is connected.  
  If another worker is already connected, the incoming worker throws a `SubscriptionInUseException`.  
* **`WaitForFree`**  
  If the subscription is in use, the worker waits for the connected worker to disconnect, 
  then takes its place.  
  This suits failover, where a standby worker waits to take over from the active one.  
* **`TakeOver`**  
  The incoming worker tries to take over the existing connection.  
  It succeeds if the connected worker does not itself use `TakeOver`.  
   - If the takeover succeeds, the worker that has been taken over throws a `SubscriptionInUseException`.  
   - If the takeover fails, the incoming worker throws the exception instead.  

To let several workers consume the same subscription at the same time, use the `Concurrent` strategy.
See [Concurrent subscriptions](../../data-subscriptions/concurrent-subscriptions.mdx).

<ContentFrame>

### First worker to connect sets the subscription mode

The first worker to connect sets whether the subscription runs in single-worker or concurrent mode,
and this mode holds until all workers disconnect:

* A subscription running concurrent workers admits only other concurrent workers. A worker that uses
  a single-worker strategy is rejected with `SubscriptionInUseException`.
* A subscription running a single-worker strategy admits no concurrent worker until the connected
  worker disconnects. A concurrent worker is rejected with `SubscriptionInUseException`.

</ContentFrame>

</Panel>

<ContentFrame>

### Connection failures

When an error interrupts the worker's communication with the server, the worker tries to reconnect.  
The worker keeps retrying even when it cannot reach any server, or when the cluster has no leader to
name the node responsible for the subscription, until the period set in `MaxErroneousPeriod` passes
(see [Reconnection and timeouts](../../data-subscriptions/consuming-subscription.mdx#reconnection-and-timeouts)).

The worker stops without reconnecting in these cases:

* The subscription does not exist (e.g., it was deleted).  
* The subscription is in use by another worker, or another worker took it over
  (see [Worker strategies](../../data-subscriptions/consuming-subscription.mdx#worker-strategies)).  
* The subscription was disabled, or the worker's connection was dropped
  (see [Dropping a connection](../../data-subscriptions/maintenance-operations.mdx#dropping-a-connection)).  
* The worker failed to connect for longer than `MaxErroneousPeriod`.  
* The subscription cannot run in its current state (e.g., a revisions subscription on a collection
  whose revisions are disabled).  
* An authorization error occurred.  
* The database does not exist.  
* Your batch-processing code threw an exception, and `IgnoreSubscriberErrors` is not set
  (see [Errors while processing a batch](../../data-subscriptions/consuming-subscription.mdx#errors-while-processing-a-batch)).  
* The worker runs with `CloseWhenNoDocsLeft` and no documents are left
  (see [End when no documents are left](../../data-subscriptions/consuming-subscription.mdx#example-end-when-no-documents-are-left)).  

---

When the worker stops instead of reconnecting, the task returned by `Run` completes in error.  
To follow the worker's connection and reconnection attempts,
see [Worker status](../../data-subscriptions/consuming-subscription.mdx#worker-status).

</ContentFrame>

<ContentFrame>

### Errors while processing a batch

When your batch-processing code throws an exception, the worker's response depends on the
`IgnoreSubscriberErrors` option of the `SubscriptionWorkerOptions` object:

* **`false`** (default)  
  Processing stops. The worker wraps the exception in a `SubscriberErrorException` and rethrows
  it without acknowledging progress, so the task returned by `Run` completes in error.  
* **`true`**  
  The failed batch is acknowledged without a retry, and the worker continues with the next
  batches.  

</ContentFrame>

<ContentFrame>

### Reconnection and timeouts

These `SubscriptionWorkerOptions` properties govern reconnection and connection timeouts:

* **`TimeToWaitBeforeConnectionRetry`**  
  How long the worker waits before each reconnect attempt.  
  Default: 5 seconds.  
* **`MaxErroneousPeriod`**  
  How long the worker may keep failing to reconnect, counted from the first failure since its last successful
  connection, before the worker stops retrying.  
  Default: 5 minutes.  
* **`ConnectionStreamTimeout`**  
  How long the worker waits for data from the server, or for a write to the server to complete,
  before treating the connection as broken and trying to reconnect.  
  Default: 30 seconds. Cannot be set below 15 seconds.  

```csharp
var options = new SubscriptionWorkerOptions(subscriptionName);

// Set the worker's timeout period
options.ConnectionStreamTimeout = TimeSpan.FromSeconds(45);
```

### Status and state changes

To check the worker's current activity (e.g., whether the worker is connected to the server), read the worker's `Status` property.  
The `Status` property returns a [SubscriptionWorkerStatus](../../data-subscriptions/consuming-subscription.mdx#classes) object,
whose `State` property holds one of the following states:

* **`NotStarted`**  
  The worker was created, but `Run` has not been called yet.  
* **`Connecting`**  
  The worker is connecting to the subscription, at startup or before a reconnection.  
* **`WaitingForDocuments`**  
  The worker is connected and waiting for the next batch.  
* **`Processing`**  
  Your processing code is handling a batch.  
  This state lasts until the worker acknowledges the batch to the server.  
* **`Retrying`**  
  The connection failed, and the worker is waiting to reconnect
  (see [Connection failures](../../data-subscriptions/consuming-subscription.mdx#connection-failures)).  
* **`Faulted`**  
  The worker stopped without reconnecting, and the task returned by `Run` completed in error.  
* **`Stopped`**  
  The worker was disposed, or the cancellation token passed to `Run` was canceled.  

Once the worker reaches `Faulted` or `Stopped`, the worker's state no longer changes.

When the state is `Retrying` or `Faulted`, the `Exception` property of the `SubscriptionWorkerStatus` object holds the failure
that caused the state.  
If the worker fails repeatedly, the `Exception` property holds the latest failure.  
The `FailingSinceUtc` property of the `SubscriptionWorkerStatus` object holds the time of the first failure since the worker's
last successful connection, or `null` while the worker is connected.

Read `Status` when your application needs the worker's state at a specific moment (e.g., when a health check runs).  
To be notified of every state change as soon as the change happens (e.g., to raise an alert when the worker starts retrying),
subscribe to the worker's `OnStateChanged` event.  
The event passes the worker and the worker's new status (a `SubscriptionWorkerStatus` object) to your handler.  
The worker does not continue until your handler returns, so avoid long-running or blocking work in the handler:
a handler that never returns keeps the worker from continuing.  
If the handler throws an exception, the worker catches the exception and continues.

```csharp
// FailingSinceUtc is null while the worker is connected, and is set while the worker is failing
SubscriptionWorkerStatus status = subscriptionWorker.Status;
if (status.FailingSinceUtc != null)
    Console.WriteLine($"Failing since {status.FailingSinceUtc}: {status.Exception?.Message}");

// Write each change of the worker's state to the console
subscriptionWorker.OnStateChanged += (worker, newStatus) =>
{
    Console.WriteLine($"Worker state: {newStatus.State}");
};
```

### Worker events

<Admonition type="note" title="">

The worker's events are standard C# events: attach a handler to an event using `+=`, and detach the handler using `-=`
(see [Subscribing to store events](../../client-api/how-to/subscribe-to-store-events.mdx), which shows both operations
on the document store's events).  
To detach a handler later, keep a reference to the handler when you attach it (e.g., use a named method rather than
a lambda expression), since `-=` must receive the same handler.

</Admonition>

To react to the worker's connections, failures, acknowledged batches, and disposal, subscribe to these worker events:

* **`OnEstablishedSubscriptionConnection`**  
  Fires each time the worker connects to the subscription, both the first time and after every reconnection.  
* **`OnUnexpectedSubscriptionError`**  
  Fires when the worker hits an error it does not recognize (e.g., a dropped network connection),
  before the worker waits to reconnect.  
* **`OnSubscriptionConnectionRetry`**  
  Fires each time the worker is about to reconnect, after the wait set in `TimeToWaitBeforeConnectionRetry`.  
* **`AfterAcknowledgment`**  
  Fires after the server acknowledges the progress of a processed batch.  
* **`OnDisposed`**  
  Fires after the worker is disposed.  

When the worker stops instead of reconnecting, neither `OnUnexpectedSubscriptionError`
nor `OnSubscriptionConnectionRetry` fires.

The following code writes a message to the console on each connection, unrecognized error, and reconnection attempt:

```csharp
// Fires on the first connection and after every reconnection
subscriptionWorker.OnEstablishedSubscriptionConnection += () =>
{
    Console.WriteLine("Connected to the subscription");
};

// Fires for an error the worker does not recognize, before the wait
subscriptionWorker.OnUnexpectedSubscriptionError += exception =>
{
    Console.WriteLine($"Unexpected subscription error: {exception.Message}");
};

// Fires before each reconnection attempt, after the wait
subscriptionWorker.OnSubscriptionConnectionRetry += exception =>
{
    Console.WriteLine($"Reconnecting to the subscription after: {exception.Message}");
};
```

### Example: Full exception handling with retries

In this example, the client handles the exceptions the worker may throw, 
recreating the worker to resume processing when the error is recoverable.

```csharp
while (true)
{
    // Create the worker:
    var options = new SubscriptionWorkerOptions(subscriptionName);

    // Configure the worker:
    // Allow a downtime of up to 2 hours,
    // and wait 2 minutes before reconnecting
    options.MaxErroneousPeriod = TimeSpan.FromHours(2);
    options.TimeToWaitBeforeConnectionRetry = TimeSpan.FromMinutes(2);

    subscriptionWorker = store.Subscriptions.GetSubscriptionWorker<Order>(options);

    try
    {
        // Before each reconnection attempt, write the error that caused it to the console
        subscriptionWorker.OnSubscriptionConnectionRetry += exception =>
        {
            Console.WriteLine($"Reconnecting to the subscription after: {exception.Message}");
        };

        // Run the worker:
        await subscriptionWorker.Run(batch =>
        {
            foreach (var item in batch.Items)
            {
                // Forcefully stop subscription processing if the order's Company is "companies/2-A"
                // and throw an exception to let external logic handle the specific case
                if (item.Result.Company == "companies/2-A")
                {
                    // The custom exception thrown from here
                    // will be wrapped by `SubscriberErrorException`
                    throw new UnsupportedCompanyException(
                        "Company ID cannot be 'companies/2-A', please fix");
                }

                // Process the order document - provide your own logic
                ProcessOrder(item.Result);
            }
        }, cancellationToken);

        // The Run method will stop if the subscription worker is disposed,
        // exiting the while loop
        return;
    }
    catch (Exception e)
    {
        Console.WriteLine($"Failure in subscription {subscriptionName}: {e.Message}");

        // The following exceptions are not recoverable
        if (e is DatabaseDoesNotExistException ||
            e is SubscriptionDoesNotExistException ||
            e is SubscriptionInvalidStateException ||
            e is AuthorizationException)
            throw;

        if (e is SubscriptionClosedException)
            // Subscription probably closed explicitly by admin
            return;

        if (e is SubscriberErrorException se)
        {
            // For UnsupportedCompanyException we want to throw an exception,
            // otherwise, continue processing
            if (se.InnerException != null && se.InnerException is UnsupportedCompanyException)
            {
                throw;
            }

            // Call continue to skip the current while(true) iteration and try reconnecting
            // in the next one, allowing the worker to process future batches.
            continue;
        }

        // Handle this depending on the subscription opening strategy
        if (e is SubscriptionInUseException)
            continue;

        // Call return to exit the while(true) loop,
        // dispose of the worker (via finally), and stop the subscription.
        return;
    }
    finally
    {
        subscriptionWorker.Dispose();
    }
}
```

### Example: Processing documents in a session

In this example, the subscription sends to the worker `Orders` that have no shipping date.  
The worker sets each document's `ShippedAt` field and saves it back through a session.

<Admonition type="info" title="">
Open the session using `batch.OpenSession`, not `store.OpenSession`.
</Admonition>

```csharp
// Create the subscription task on the server:
var subscriptionName = store.Subscriptions.Create(new SubscriptionCreationOptions()
{
    Query = @"from Orders as o where o.ShippedAt = null"
});

// Create the subscription worker that will consume the documents:
var subscriptionWorker = store.Subscriptions.GetSubscriptionWorker<Order>(subscriptionName);
var subscriptionRuntimeTask = subscriptionWorker.Run(batch =>
{
    // Open a session using 'batch.OpenSession'
    using (var session = batch.OpenSession())
    {
        foreach (var order in batch.Items.Select(x => x.Result))
        {
            TransferOrderToShipmentCompany(order); // call your custom method
            order.ShippedAt = DateTime.UtcNow;     // update the document field
        }

        // Save the updated Order documents
        session.SaveChanges();
    }
});
```

### Example: End when no documents are left

In this example, the worker runs until no new documents remain, which suits ad-hoc, single-use processing where
you need every matching document processed once.  
Set `CloseWhenNoDocsLeft` to `true`; the worker then throws a `SubscriptionClosedException` when
it finishes.

```csharp
// Create the subscription task on the server:
var subscriptionName = store.Subscriptions.Create<Order>(
    new SubscriptionCreationOptions<Order>
    {
        Filter = order => order.Lines.Sum(line => line.PricePerUnit * line.Quantity) > 10000,
        Projection = order => new OrderAndCompany
        {
            OrderId = order.Id,
            Company = RavenQuery.Load<Company>(order.Company)
        }
    });

// Create the subscription worker that will consume the documents:
var highValueOrdersWorker = store.Subscriptions.GetSubscriptionWorker<OrderAndCompany>(
    new SubscriptionWorkerOptions(subscriptionName)
    {
        // Here we set the worker to stop when there are no more documents left to send
        // Will throw SubscriptionClosedException when it finishes its job
        CloseWhenNoDocsLeft = true
    });

try
{
    await highValueOrdersWorker.Run(batch =>
    {
        foreach (var item in batch.Items)
        {
            SendThankYouNoteToCompany(item.Result); // call your custom method
        }
    });
}
catch (SubscriptionClosedException)
{
    // That's expected, no more documents to process
}
```

### Example: Including documents in the batch

In this example, the subscription sends to the worker every `Order` and includes in the batch
`Product` documents referenced in the order.  
When the worker accesses an included `Product`, the product's data has already arrived in the batch,
so the worker does not need to fetch the product from the server.

```csharp
// Create the subscription task on the server:
var subscriptionName = store.Subscriptions.Create(new SubscriptionCreationOptions()
{
    // Include the referenced Product documents for each Order document
    Query = @"from Orders include Lines[].Product"
});

// Create the subscription worker that will consume the documents:
var subscriptionWorker = store.Subscriptions.GetSubscriptionWorker<Order>(subscriptionName);
var subscriptionRuntimeTask = subscriptionWorker.Run(batch =>
{
    // Open a session using 'batch.OpenSession' to access the Product documents
    using (var session = batch.OpenSession())
    {
        foreach (var order in batch.Items.Select(x => x.Result))
        {
            foreach (var orderLine in order.Lines)
            {
                // Calling Load will not generate a request to the server,
                // since orderLine.Product was included in the batch
                var product = session.Load<Product>(orderLine.Product);

                ProcessOrderAndProduct(order, product); // call your custom method
            }
        }
    }
});
```

### Example: Standby workers on several machines

In this example, the same worker code runs on several machines, all using the `WaitForFree` strategy.  
One worker connects to the subscription, and the other workers wait.  
If the connected worker disconnects (e.g., when its machine goes down), one of the waiting workers connects and
continues processing.  
Unlike in the [primary and secondary workers](../../data-subscriptions/consuming-subscription.mdx#example-primary-and-secondary-workers)
example, a worker that reconnects after a failure does not take the connection back, but joins the waiting workers.

```csharp
var worker = store.Subscriptions.GetSubscriptionWorker<Order>(
    new SubscriptionWorkerOptions(subscriptionName)
    {
        // WaitForFree: wait and take over if the connected worker fails
        Strategy = SubscriptionOpeningStrategy.WaitForFree
    });
```

</ContentFrame>

    try
    {
        await primaryWorker.Run(x =>
        {
            // your logic
        });

    catch (Exception)
    {

}

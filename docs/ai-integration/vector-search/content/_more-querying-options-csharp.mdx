<Panel heading="Exact search">

* By default, vector searches use the **Approximate Nearest-Neighbor (ANN)** method,  
  which uses the HNSW graph to find similar vectors efficiently.  

* You can explicitly request **exact search** to scan the relevant vectors and find the actual closest matches.  
  This provides greater accuracy at a higher computational cost.  

* To request exact search, set `isExact: true` in the Client API,  
  or wrap `vector.search(...)` with `exact(...)` in RQL.  
  Exact search supports both text and numerical content.  

* Learn about the accuracy and performance tradeoffs in
  [What affects vector search results](../../../ai-integration/vector-search/what-affects-vector-search-results.mdx#using-exact-search).

### How filtered vector search works    

When a vector search query is combined with a filtering condition using **AND** (e.g., `where vector.search(...) and PricePerUnit > 35`),
RavenDB integrates the filter into the vector search process rather than running the vector search independently and discarding non-matching results afterward.  

**Internal Strategies**   
RavenDB first evaluates the filter to determine how many documents match and then dynamically selects a strategy:    
    
* **Exact search over filtered documents:**  
  This mode is triggered when any of the following conditions is true:    
    
  * The filter match count is **below** the scanning threshold (default: `1024`). Can be customized via the  
    [Indexing.Corax.VectorSearch.VectorSearchScanningThreshold](../../../ai-integration/vector-search/configuration.mdx#indexingcoraxvectorsearchvectorsearchscanningthreshold) configuration key.
  * An [Exact search](#exact-search) is explicitly requested.  
  * The requested _number of candidates_ exceeds half the filter match count.  
    Learn about the `numberOfCandidates` parameter in [The query parameters](../../../ai-integration/vector-search/vector-search-using-dynamic-query.mdx#the-dynamic-query-parameters).
    
  In this mode, an exact search is performed over **only** the documents that match the filter.   

* **Approximate search:**  
  When none of the conditions above apply, RavenDB uses approximate HNSW graph traversal to find the nearest vectors to the search term.
  The filter is applied to the documents associated with the candidate vectors.  
    
  If fewer than the requested _number of candidates_ have matching documents,
  RavenDB repeats the HNSW search with a larger internal candidate count while its search limits allow.  
    
  This process attempts to retrieve additional candidates that satisfy both the similarity requirement and the filter.  
  The number of matching candidates returned can still be lower than requested because of the similarity threshold or internal search limits.
    
  Note:    
  Re-search rounds are efficient because RavenDB caches the HNSW graph's internal state (including previously computed results), 
  avoiding redundant distance calculations for previously visited nodes.    
    
</Admonition>

### Dynamic query {/* #multiple-vector-searches-dynamic-query */}    

* The following query uses semantic similarity comparisons and returns companies in either of these cases:  
  * `Name` is similar to `"snack"` **AND** `Address.Country` is similar to `"europe"`.
  * `Name` is similar to `"dairy"`.

* Running the query example on the RavenDB sample data will generate the following auto-index:  
  `Auto/Companies/ByVector.search(embedding.text(Address.Country))AndVector.search(embedding.text(Name))`.  
  This index includes two vector fields: `Address.Country` and `Name`.

<Tabs groupId='languageSyntax'>
<TabItem value="DocumentQuery" label="DocumentQuery">
```csharp
var companies = session.Advanced
    .DocumentQuery<Company>()
     // Use OpenSubclause & CloseSubclause to differentiate between clauses:
     // ====================================================================
    
    .OpenSubclause()
    .VectorSearch( // Search for companies that sell snacks or similar
        field => field.WithText(x => x.Name),
        searchTerm => searchTerm.ByText("snack"),
        minimumSimilarity: 0.78f
    )
     // Use 'AndAlso' for an AND operation
    .AndAlso()
    .VectorSearch( // Compare the country name with 'europe'
        field => field.WithText(x => x.Address.Country),
        searchTerm => searchTerm.ByText("europe"),
        minimumSimilarity: 0.82f
    )
    .CloseSubclause()
     // Use 'OrElse' for an OR operation
    .OrElse()
    .OpenSubclause()
    .VectorSearch( // Search for companies that sell dairy products or similar
        field => field.WithText(x => x.Name),
        v => v.ByText("dairy"),
        minimumSimilarity: 0.80f
    )
    .CloseSubclause()
    .WaitForNonStaleResults()
    .ToList();
```
</TabItem>
<TabItem value="DocumentQuery_async" label="DocumentQuery_async">
```csharp

    .VectorSearch(
        field => field.WithText(x => x.Address.Country),

    .OrElse()
    .OpenSubclause()
```

<Admonition type="info" title="">

**How multiple vector search clauses are evaluated**:

* The logical operators determine how matches are combined:  
  * **OR** combines the results of separately evaluated vector searches.  
    A document can match either clause.  
  * **AND** requires a document to match every clause.  
    RavenDB can use the matches from one vector clause as a filter for another.  

* The `numberOfCandidates` parameter limits the number of matching vectors returned **per query vector**  
  in each clause.
  * A clause has **several query vectors** when you pass multiple search terms with `ByTexts`,  
    or when the embeddings generation task splits the search term into chunks.  
    RavenDB runs a separate search for each query vector and merges the results.
  * You can set `numberOfCandidates` separately for each clause; see [query parameters](../../../ai-integration/vector-search/vector-search-using-dynamic-query.mdx#the-dynamic-query-parameters).  
  * If omitted, the value comes from [Indexing.Corax.VectorSearch.DefaultNumberOfCandidatesForQuerying](../../../ai-integration/vector-search/configuration.mdx#indexingcoraxvectorsearchdefaultnumberofcandidatesforquerying) (default: `16`).  

* Increasing the _number of candidates_ expands the candidate pool and can help combined queries find more matches,
  at the cost of additional search work.

</Admonition>

</Panel>

<Panel heading="Retrieving matching chunk text">

* When an [embeddings generation task](../../../ai-integration/generating-embeddings/embeddings-generation-task.mdx) splits a long text field into chunks,
  a vector search returns the documents that match the search term. By default, the matching chunk text is not included.

* If the task stores the text of each chunk, you can also retrieve the matching chunks of each returned document
  using the [highlighting](../../../client-api/session/querying/text-search/highlight-query-results.mdx) API.
  The matching chunks are returned as highlight fragments, nearest to the search term first.

* **Prerequisites**:  
    
  * The searched field must be one that an embeddings generation task generates embeddings for,  
    and the query must provide the search term as **text**.  
    See [Supported queries and limitations](#supported-queries-and-limitations).
    
  * The task must have its `StoreChunkText` option enabled.  
    This option is off by default and applies only to documents the task processes after it is enabled.  
    It cannot currently be set in the Studio; set it through the Client API.  
    Learn how to enable it and how to reprocess existing documents in
    [Store chunk text](../../../ai-integration/generating-embeddings/embeddings-generation-task.mdx#store-chunk-text).
    
  * Wait for the task to finish processing the relevant documents, including any requested reprocessing.  
    Monitor the embeddings generation task's progress in the [Studio's AI Tasks view](../../../ai-integration/ai-tasks-list-view) and wait until it is up to date, including after reprocessing existing documents.
    `WaitForNonStaleResults` in the examples waits for indexing; it does not wait for the embeddings generation task to finish.
    
  * The index must store the vectors in the same quantization format as the task.  
    See [Supported queries and limitations](#supported-queries-and-limitations) for details.

* The examples below use the task defined in
  [this example](../../../ai-integration/generating-embeddings/embeddings-generation-task.mdx#store-chunk-text).  
  The task generates embeddings from the `Notes` field of _Employee_ documents and stores the text of each chunk.

### Dynamic query {/* #chunk-text-dynamic-query */}

* The following example searches for _Employee_ documents whose `Notes` are similar to the search term  
  `"speaks foreign languages"`, and retrieves the matching chunks of each returned document.

### Reading the fragments

* For the `Query` (LINQ) and `DocumentQuery` examples above -  
  call `notesHighlights.GetFragments(documentId)` to read a document's matching chunks.
* For the `RawQuery` examples above -  
  read the `highlightings` dictionary captured in `AfterQueryExecuted`.

* Learn more about the `Highlightings` object in [Highlight search results](../../../client-api/session/querying/text-search/highlight-query-results.mdx#syntax).

    <Tabs groupId='fragmentReading'>
    <TabItem value="Highlight" label="Query (LINQ) / DocumentQuery">

    `GetFragments` returns the matching chunks nearest to the search term first.  
    A document with no matching chunk text returns an empty array.

    ```csharp
    foreach (var employee in employees)
    {
        // The matching chunks of this employee's notes, nearest first
        string[] fragments = notesHighlights.GetFragments(employee.Id);
    
        foreach (var fragment in fragments)
        {
            Console.WriteLine($"{employee.Id}: {fragment}");
        }
    }
    ```
    </TabItem>
    <TabItem value="RawQuery" label="RawQuery (RQL)">

    A field or document ID can be absent when no fragments were returned.  
    Use `TryGetValue` to read the entries safely.

    ```csharp
    // Use "VectorFromNotes" for the static-index raw-query example.
    const string fieldName = "Notes";
    
    foreach (var employee in employees)
    {
        if (highlightings == null ||
            !highlightings.TryGetValue(fieldName, out var byDocument) ||
            !byDocument.TryGetValue(employee.Id, out var fragments))
        {
            continue;
        }
    
        foreach (var fragment in fragments)
        {
            Console.WriteLine($"{employee.Id}: {fragment}");
        }
    }
    ```
    </TabItem>
    </Tabs>

* The fragments are returned in the `Highlightings` section of the query result,
  keyed by the highlighted field name (`Notes` in the dynamic-query example, `VectorFromNotes` in the static-index example), and then by document ID.
  Each document ID maps to an array of chunk texts, nearest to the search term first:

    ```json
    "Highlightings": {
        "Notes": {
            "employees/2-A": [
                "<text of the matching chunk nearest to the search term>",
                "<text of the next matching chunk>"
            ],
            "employees/5-A": [
                "<text of the matching chunk>"
            ]
        }
    }
    ```

  and open the [Highlight tab](../../../client-api/session/querying/text-search/highlight-query-results.mdx#highlight-results-in-studio) to see the returned chunks.

### Fragment behavior

* **Which chunks are returned**:  
  RavenDB compares each stored chunk of a returned document with the search term.  
  A chunk is returned if its similarity to the search term is at or above the query's `minimumSimilarity`,  
  see [Query-time parameters](../../../ai-integration/vector-search/what-affects-vector-search-results.mdx#query-time-parameters).  

  The default minimum similarity is `0`, so unless you set `minimumSimilarity`,  
  every stored chunk of a returned document qualifies.

* **Order and number of chunks**:  
  In the query results, the first element of each document's fragments array contains the chunk most similar to the search term.
  The remaining chunks follow in decreasing order of similarity.  

  `fragmentCount` ([Highlight syntax](../../../client-api/session/querying/text-search/highlight-query-results.mdx#syntax)) sets the maximum number of chunks returned per document.  
  Set it to `0` to return all qualifying chunks.

* **Fragment length**:  
  `fragmentLength` ([Highlight syntax](../../../client-api/session/querying/text-search/highlight-query-results.mdx#syntax)) limits each fragment to that many characters from the beginning of the chunk;
  longer chunk text is cut off. Set it to `0` to return the full chunk text.  
  Unlike full-text highlighting, the fragment is not built around a matched term.

* **Context prefix**:  
  The stored text is the text that was sent to the embedding model,
  so it starts with the chunk's [context prefix](../../../ai-integration/generating-embeddings/chunking-and-context-prefixes.mdx#adding-a-context-prefix-to-chunks),  
  if one is defined. The prefix counts toward `fragmentLength`.

* **No highlight tags**:  
  Chunk fragments are returned as plain text.  
  The `PreTags` and `PostTags` [highlighting options](../../../client-api/session/querying/text-search/highlight-query-results.mdx#highlight---customize-tags) don't apply to them.

* **Exact and approximate search**:  
  The stored chunks of each returned document are compared with the search term directly,  
  whether the query uses [exact search](#exact-search) or the default approximate search.

* **Vector search with additional `where` conditions**:  
  Chunks are retrieved for each document the query returns,  
  including when the vector search is [combined with other `where` conditions](#combining-vector-search-with-other-where-conditions).

* **Multiple search terms**:  
  * When the search term produces several embeddings, each chunk is compared with the search-term embedding nearest to it.
    For example, when several terms are passed with `ByTexts`, or when the task splits a long search term into chunks.
  * When the query runs [multiple vector searches](#combining-multiple-vector-searches) on the same field using the same task,  
    the search terms of all these searches are used, and the lowest `minimumSimilarity` among them applies.

* **Full-text and vector search on the same field**:  
  When a dynamic query runs both a full-text `Search` and a vector search on the same document field and highlights that field:

  * Each returned document's fragments array contains **full-text fragments first**,  
    followed by the matching chunk fragments.
  * Only the full-text fragments contain highlight tags.
  * A positive `fragmentCount` limits each group separately,  
    so the combined array can contain more than `fragmentCount` fragments.
  * Setting `fragmentCount` to `0` returns all qualifying chunk fragments, but no full-text fragments.

</Admonition>

### Supported queries and limitations

* **Supported queries**:  
  Chunk text is retrieved for vector searches on embeddings generated by an embeddings generation task,  
  when the search term is provided as text:
  * Dynamic queries that specify the task with `UsingTask`  
    (`embedding.text(<field>, ai.task('<task-identifier>'))` in RQL).
  * Queries on static index fields that load the task's embeddings with `LoadVector`.

* **Unsupported queries**:  
  The following vector searches run as usual, but return no chunk fragments:
  * Searches on raw text without a task (`embedding.text(<field>)` without `ai.task`).
  * Searches on numerical embeddings stored in your documents,  
    or on index fields defined with `CreateVector`.
  * Searches for similar documents (`embedding.forDoc`),  
    or searches with a raw vector (`embedding.forRaw`).

* **Documents without stored chunk text**:  
  Documents that the task processed while `StoreChunkText` was disabled have no stored chunk text,  
  so they return no chunk fragments. The query does not fail.
  [Reprocess](../../../ai-integration/generating-embeddings/embeddings-generation-task.mdx#reprocess-existing-documents) them to store their chunk text.

* **Search engine**:  
  Like all vector searches, chunk text retrieval requires the [Corax](../../../indexes/search-engine/corax.mdx) search engine.

* **Sharded databases**:  
  Highlighting is not supported in [sharded databases](../../../sharding/overview.mdx).  
  Highlighting queries in a sharded database throw a `NotSupportedInShardingException`.

* **Tasks that process several fields**:  
  The task stores one chunk-text map per document, covering all the fields it processes.  
  When a task generates embeddings for several fields, highlighting one of them can currently also return matching chunks of the task's other fields.
  To retrieve chunks of a single field only, generate that field's embeddings with a task that processes only that field.

* **Related documents**:  
  When a static index uses `LoadVector` to index the embeddings of a
  [related document](../../../ai-integration/vector-search/vector-search-using-static-index.mdx#indexing-text-embeddings-generated-by-tasks---from-related-document),
  the chunk text is currently read from the embeddings document of the **returned** document, not of the related document.  
  If the related document is in a different collection than the returned document, no chunk fragments are returned.  
  If both are in the same collection, the fragments are taken from the returned document's own chunks,  
  not from the related document's chunks.

* **Quantization**:  
  Chunk fragments are currently returned only when the vector field stores the embeddings in the same format as the task.  
  If the index quantizes the task's embeddings to another format, the query returns results but no chunk fragments.  

  For example, suppose a task stores `Single` embeddings.  
  Either of these settings makes the index store them as `Int8`:

  * In a dynamic query, use `TargetQuantization(VectorEmbeddingType.Int8)`.
  * In a static index, set `DestinationEmbeddingType = VectorEmbeddingType.Int8` on the vector field.

  In both cases, the formats differ. The query can still return matching documents, but no chunk fragments are returned.
  See [Quantization and embeddings generation tasks](../../../ai-integration/vector-search/quantization.mdx#quantization-and-embeddings-generation-tasks).

</Admonition>

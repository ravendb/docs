* Use the **Patch** operation to update selected parts of a document without requiring the client to load, modify,  
  and save the full document.  
  
* The patch is sent in a single request and applied atomically by the server in a single write [transaction](../../../../client-api/faq/transaction-support.mdx).  
  This reduces client-server traffic and is especially useful when updating denormalized data.

### Session API

The `session.advanced()` API provides the following methods for common single-document patch operations:

* `patch`
* `patchArray`
* `patchObject`
* `addOrPatch`
* `addOrPatchArray`
* `increment`
* `addOrIncrement`

<ContentFrame>

#### Example: Modify a single field

```java
// Modify FirstName to Robert       
session.advanced().patch("employees/1-A", "FirstName", "Robert");

session.saveChanges();
```

</ContentFrame>
    
---
    
**Patch format**:      
Each method generates a JavaScript patch command from a predefined script template.  
The Java client does not provide an API for sending RFC 6902 JSON Patch commands.  
   
**Saving session patches**:    
Calls to these methods are queued in the [session](../../../../client-api/session/what-is-a-session-and-how-does-it-work.mdx)
and sent to the server only when [saveChanges](../../../../client-api/session/saving-changes.mdx) is called.  
`saveChanges()` sends the patch commands together with all other changes tracked by the session -  
including stored, modified, and deleted documents - as a single batch in one HTTP request.    
    
**Missing documents**:    
If the target document does not exist, session-generated `patch`, `patchArray`, `patchObject`,  
and `increment` commands make no changes, and `saveChanges()` does not throw.  
Use `addOrPatch`, `addOrPatchArray`, or `addOrIncrement` when a missing document should be created.      

**Transaction guarantees**:   
The server executes the entire batch in one ACID transaction.  
If any command in the batch fails, such as because of a patch error or a concurrency conflict on another command,  
the transaction is rolled back and none of the changes in the batch are persisted.  
When `saveChanges()` returns successfully, the entire batch has been persisted.

**Optimistic concurrency**:  
Patch commands generated by these `session.advanced()` patch methods carry no change vector,  
even when [optimistic concurrency](../../../../client-api/session/configuration/how-to-enable-optimistic-concurrency.mdx) is enabled.  
Consequently, these generated patch commands are not rejected merely because the target document changed after the patch was queued.  
    
Another command in the batch - such as a stored document or an explicitly deferred
[PatchCommandData](#session-api-using-defer-syntax) that supplies a change vector - can still fail with a concurrency conflict.

**Merging patches for the same document**:    
While a patch command is already queued for a document, a subsequent `patch`, `patchArray`, `patchObject`,  
or `increment` call for that same document is merged into the pending command rather than queued as a new one.  
The scripts are concatenated in call order and their parameter values are combined,  
so all the changes are applied by a single script in the same transaction.  
Reversing the call order can still change the final value when two calls modify the same field.

**Removals that target missing elements**:    
An out-of-range `removeAt` on an array, or a `remove` of a key that is not present in an object,  
is applied as a JavaScript no-op. No exception is thrown, and the other changes in the batch are still applied.

</Admonition>

### Session API using Defer

* Use `session.advanced().defer` to queue a low-level patch command instead of using the  
  `session.advanced()` patch methods. Defining the command yourself gives you full control over the  
  patch script and access to options the wrapper methods do not expose.

* Create a `PatchRequest` containing a JavaScript script and optional parameter values,  
  then pass it in a `PatchCommandData` for the document you want to patch.  
  `PatchCommandData` also accepts an optional `changeVector`, which enforces optimistic concurrency  
  for the patch, and an optional `patchIfMissing` script, which runs when the document does not exist.  
  The `session.advanced()` patch methods expose neither option.
    
  `PatchCommandData` also has a `createIfMissing` property,  
  which supplies a full document to store when the target document does not exist, instead of a script to run.    

* `defer` adds the `PatchCommandData` to the session's unit of work.  
  The command is sent to the server only when `saveChanges()` is called,  
  together with the session's other pending changes in a single request and transaction.

<ContentFrame>

#### Example: Modify a single field

```java
// Modify FirstName to Robert     
PatchRequest patchRequest = new PatchRequest();
patchRequest.setScript("this.FirstName = args.FirstName;");
patchRequest.setValues(Collections.singletonMap("FirstName", "Robert"));

session.advanced().defer(new PatchCommandData(
    "employees/1-A", // id
    null,            // changeVector
    patchRequest,    // patch
    null));          // patchIfMissing

session.saveChanges();
```

</ContentFrame>

**Deferred and immediate execution**:    
`PatchCommandData` implements `ICommandData`, which represents command data included in a batch;  
it is not a [RavenCommand](../../../../client-api/commands/overview.mdx) that can be executed directly through a request executor.  
To send a single-document patch without waiting for `saveChanges()`, use the [Operations API](#operations-api) described below.

**Mixing deferred and wrapper-method patches**:    
Avoid calling `session.advanced().patch` after deferring a `PatchCommandData` for the same document in the same session.
The patch call is merged into the deferred command, but the merge does not preserve the deferred command's
`changeVector`, `patchIfMissing` script, or `createIfMissing` document.  
    
To keep the changes in one transaction, express them all in the deferred script;  
otherwise, send them in separate `saveChanges()` calls or sessions.

</Admonition>

### Operations API

* **Creating and executing the operation**:  
  Use the [Operations API](../../../../client-api/operations/what-are-operations.mdx) to patch a single document directly through the document store,  
  without opening a session.

  Create a `PatchRequest` containing a JavaScript script and optional parameter values, then pass it to `PatchOperation`
  together with the document ID and any optional concurrency or missing-document settings.

  Execute the operation with `store.operations().send()`. Unlike a deferred session command,  
  the patch is sent to the server immediately in its own HTTP request and its own transaction,  
  and does not wait for `saveChanges()`. Separate operations are therefore not applied atomically together.

<ContentFrame>

#### Example: Modify a single field

```java
// Modify FirstName to Robert     
PatchRequest patchRequest = new PatchRequest();
patchRequest.setScript("this.FirstName = args.FirstName;");
patchRequest.setValues(Collections.singletonMap("FirstName", "Robert"));

store.operations().send(new PatchOperation(
    "employees/1-A", // id
    null,            // changeVector
    patchRequest));  // patch
```

</ContentFrame>

* **Patch status**:  
  `send` returns the resulting `PatchStatus`.  
  If no document with the given ID is found and no `patchIfMissing` script was provided,  
  the returned status is `DOCUMENT_DOES_NOT_EXIST` and no exception is thrown.  

  If `skipPatchIfChangeVectorMismatch` is `true`, a change-vector mismatch skips the patch and is reported  
  as `NOT_MODIFIED`. With the default `false`, a mismatch throws a `ConcurrencyException` instead.

* **Returning the document**:  
  To have the patched document returned and deserialized into one of your own classes, pass the entity class as the first argument to `send`.
  This overload returns a `PatchOperation.Result` object that holds the patch `status` and the resulting `document`.
        
  `document` contains the resulting document when the status is `CREATED` or `PATCHED`.  
  It is also populated when the patch executes but makes no changes and returns `NOT_MODIFIED`.  
  It is not set when the target document does not exist and no `patchIfMissing` script was supplied,  
  or when the server skips the patch.  
        
  See [Operations API syntax](#operations-api-syntax) for the method signatures and the `PatchOperation.Result` properties.

</Admonition>

### Session API using Defer syntax

The non-typed Session API for patches uses the `session.advanced().defer` function which allows registering one or more commands.  
One of the possible commands is the `PatchCommandData`, describing single document patch command.  
The patch request will be sent to the server only when calling `saveChanges`, this way it's possible to perform multiple operations in one request to the server.  

#### `session.advanced().defer`
        
<TabItem value="patch_defer_in_session" label="patch_defer_in_session">
```java
void defer(ICommandData command, ICommandData... commands);

void defer(ICommandData[] commands);
```
</TabItem>

| Parameter    | Type             | Description                                                                                                |
| ------------ | ---------------- | ---------------------------------------------------------------------------------------------------------- |
| **command**  | `ICommandData`   | Command that will be executed on the server.<br/>Use the `PatchCommandData` command for patching.          |
| **commands** | `ICommandData[]` | List of commands that will be executed on the server.<br/>Use the `PatchCommandData` command for patching. |

<Admonition type="info" title="">

#### PatchCommandData

<TabItem value="class_PatchCommandData" label="class_PatchCommandData">
```java
PatchCommandData(String id, String changeVector, PatchRequest patch);

PatchCommandData(String id, String changeVector, PatchRequest patch,
    PatchRequest patchIfMissing);
```
</TabItem>

| Constructor        | Type           | Description                                                                                                                              |
| ------------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **id**             | `String`       | ID of the document to be patched.                                                                                                        |
| **changeVector**   | `String`       | [Can be null] Change vector of the document to be patched, used to verify that the document was not changed before the patch reached it. |
| **patch**          | `PatchRequest` | Patch request to be performed on the document.                                                                                           |
| **patchIfMissing** | `PatchRequest` | [Can be null] Patch request to be performed if no document with the given ID was found.                                                  |

| Property             | Type         | Description                                                                                                                            |
| -------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| **createIfMissing**  | `ObjectNode` | [Can be null] Document to create if no document with the given ID was found, instead of running a script.<br/>Set with `setCreateIfMissing`. |

</Admonition>

<Admonition type="info" title="">

#### PatchRequest

We highly recommend using scripts with parameters. This allows RavenDB to cache scripts and boost performance. 
Parameters can be accessed in the script through the `args` object and passed using PatchRequest's "values" property.

| Property   | Type                  | Description                                                                                                                        |
| ---------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **script** | `String`              | The patching script, written in JavaScript.<br/>Set with `setScript`.                                                                |
| **values** | `Map<String, Object>` | Parameters to be passed to the script.<br/>Set with `setValues`.<br/>Each parameter is accessed in the script as a property of `args`, e.g. `args.FirstName`. |

* For a script that needs no parameters, `PatchRequest.forScript(script)` creates the request in a single call.

</Admonition>

### Operations API syntax

An operations interface that exposes the full functionality and allows performing ad-hoc patch operations without creating a session.  

The methods are exposed by the `OperationExecutor`, which is available as `store.operations()`.  

<TabItem value="patch_in_store" label="patch_in_store">

    PatchOperation operation);

<TEntity> PatchOperation.Result<TEntity> send(Class<TEntity> entityClass,

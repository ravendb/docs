<Admonition type="note" title="">

* **RVN002** detects query operators placed after a `ProjectInto` or `Select` projection where they can refer to the wrong fields.

* **Default severity**: _Info_  
  **Automated code fix**: _No_

<Panel heading="Description">

RavenDB LINQ query operators such as `Where`, `OrderBy`, `Search`, `Spatial`, `VectorSearch`, `Filter`, `GroupBy`,  
and their variants bind against the **source document or index fields**.
    
A projection such as `.ProjectInto<T>()` or `.Select(x => new { … })` can change the query's element type.  
A lambda passed to an operator after the projection refers to members of the projected type, while the server still uses the source fields.
If a projected member's name does not match its source field's name, the query can silently produce incorrect results or throw at runtime.

RVN002 reports operator and projection combinations that can cause these problems.  
A reported query may still work when the referenced field names match; see [Limitations](#limitations).

</Panel>

<Panel heading="Operators flagged by RVN002">

<ContentFrame>

### After `ProjectInto`

After `ProjectInto`, the following operators are flagged:  
  - **Filtering:** `Where`, `Filter`.
  - **Ordering:** `OrderBy`, `OrderByDescending`, `ThenBy`, `ThenByDescending`.
  - **Ordering by score:** `OrderByScore`, `OrderByScoreDescending`, `ThenByScore`, `ThenByScoreDescending`.
  - **Search:** `Search`, `MoreLikeThis`, `VectorSearch`.
  - **Spatial:** `Spatial`, `OrderByDistance`, `OrderByDistanceDescending`.
  - **Grouping:** `GroupBy`, `GroupByArrayValues`, `GroupByArrayContent`.

</ContentFrame>
<ContentFrame>

### After `Select`

After `Select`, the operators listed under [After `ProjectInto`](#after-projectinto) are flagged, with the exceptions below.

`Where`, `OrderBy`, `OrderByDescending`, `ThenBy`, and `ThenByDescending` are not flagged when the `Select` either:    
  - Returns the source element unchanged, such as `o => o`.
  - Creates an anonymous object in which **every member** directly copies a top-level member of the lambda parameter under the same name,  
    such as `o => new { o.Company, o.Total }` or `o => new { Company = o.Company }`.

They are flagged after other projection forms, including renamed or computed members, nested member paths, DTO projections,
and members read from captured variables, such as `o => new { captured.Name }`.

</ContentFrame>
<ContentFrame> 
    
### Operators not flagged

Operators not in the list above, such as `Include`, `Skip`, and `Take`, are not flagged after a projection.
    
</ContentFrame>    

</Panel>

<Panel heading="Trigger condition">

<ContentFrame>

### When is RVN002 reported?

RVN002 checks explicit method calls in RavenDB LINQ queries (`session.Query<T>()`, sync or async).  
RVN002 is reported on the name of each flagged operator that follows `ProjectInto` or `Select`,
according to the conditions described in [Operators flagged by RVN002](#operators-flagged-by-rvn002).

For each operator, RVN002 uses the nearest preceding `ProjectInto` or `Select` in the chain to determine which conditions apply.

RVN002 follows projected queries through local-variable initializers,
so a flagged operator can appear in a later statement that uses the local variable.

</ContentFrame>
<ContentFrame>

### When is RVN002 not reported?

- Operators placed before a projection, or not listed under [Operators flagged by RVN002](#operators-flagged-by-rvn002).
- `Where`, `OrderBy`, `OrderByDescending`, `ThenBy`, and `ThenByDescending` after a `Select` that meets the exceptions described in [After `Select`](#after-select).
- Operators and projections written as C# query-syntax clauses, such as `select … into … where …`.
- LINQ over in-memory collections, for example after `ToList()`, or other queries that do not use RavenDB's LINQ provider.

</ContentFrame>

</Panel>

<Panel heading="How to resolve">

Apply filtering, ordering, and other source-based operators **before** the projection, using the original document or index fields.
Place the projection after these operators and before materializing the results, for example via `ToList()` or `ToListAsync()`.

For `Where`, `OrderBy`, `OrderByDescending`, `ThenBy`, and `ThenByDescending` after `Select`, another option is to use an anonymous-object projection
in which every member directly copies a top-level member of the lambda parameter under the same name; see [After `Select`](#after-select).

---
    
### Before (triggers RVN002)

Here, `CompanyId` is a projection alias, not a source field.  
The `Where` must use the source field `Company` before the projection.

```csharp
var results = session.Query<Order>()
    .Select(o => new { CompanyId = o.Company })
    // Triggers RVN002: Where uses the projected alias CompanyId.
    .Where(x => x.CompanyId == "companies/1-A")
    .Take(50)
    .ToList();
```
<br/>
            
### After (correct)

```csharp
var results = session.Query<Order>()
    .Where(o => o.Company == "companies/1-A")
    .Select(o => new { CompanyId = o.Company })
    .Take(50)
    .ToList();
```

</Panel>

<Panel heading="Limitations">

- After `ProjectInto`, RVN002 reports every listed operator without checking whether the referenced field exists under the same name in the source.
  A reported query may therefore still work correctly.

- After `Select`, the exception for `Where` and the four ordering operators depends on the **entire projection**, rather than only the members used by the operator.
  A renamed or computed member causes these operators to be flagged even when they use another member that keeps its source name. For example:

  ```csharp
  .Select(o => new { o.Company, RenamedTotal = o.Total })
  .Where(x => x.Company == "companies/1-A")
  ```

- Tracking across statements is limited to local-variable initializers. Later assignments are not followed,  
  so diagnostics may be missed or based on an earlier query value.

- RVN002 does not trace a projected query through helper-method returns, parameters, fields, or properties.

</Panel>

<Admonition type="note" title="">

* An **exploration query** uses the RQL `filter` clause (the `Filter()` method in the C# API)  
  to evaluate a condition on the server against the results a query retrieves.
    
* Processing has two main stages:   
  1. **Retrieve** - the query retrieves results from a collection or an index, as defined by `from` and any `where` condition.
  2. **Filter** - the server examines the retrieved results one by one and keeps those that match the `filter` condition.  
     No index is used or created for the `filter` condition.  
     The matching results are returned to the client.

* Because `filter` examines results individually, its cost grows with the number of results it scans.  
  Use `filter_limit` to cap the number of results examined on large datasets. See [Limit the number of scanned results](#limit-the-number-of-scanned-results).  
  For recurring queries, prefer `where` when the condition can be indexed. See [When to use exploration queries](#when-to-use-exploration-queries).

<Panel heading="How exploration queries work">

C# queries written with LINQ or DocumentQuery are translated into RQL before being sent to the server.  
The processing described below applies to these APIs as well as to queries written directly in RQL.

---
    
* **An exploration query is processed on the server in two main stages**:

    1. **Retrieve**  
       The query retrieves results from the specified collection or index (static or auto), applying any initial query conditions.
       In RQL, these are specified by the `from` and `where` clauses.  
       The retrieved results are the **candidate results** for filtering.  
       If sorting is specified, it determines the order in which the filter examines them.

    2. **Filter**  
       The server examines the candidate results one by one and evaluates the filter condition using its JavaScript engine.
       Matching results are kept; results that fail the condition are skipped.  
       No index is used or created for the filter condition.

    If a projection is specified, the matching results are projected before being returned to the client.  
    Otherwise, the matching results are returned without projection.

* **What the filter condition is evaluated against**:
    * **Full documents** for full-collection queries and queries on a Map index (static or auto).  
      The filter condition can reference document fields that aren't indexed.
    * **Aggregation results** for Map-Reduce indexes and dynamic aggregation queries (`group by` in RQL).  
      Learn more in [Filter with a static Map-Reduce index](#filter-with-a-map-reduce-index-query) and [Filter with a dynamic group-by query](#filter-with-a-map-reduce-index-query-dynamic-group-by-query).

* **Filtering stops when any of the following occurs**:
    * Enough results have been collected to fill the requested page. See [Filter and paging](#filter-and-paging).
    * No further candidates remain to be examined.
    * The number of examined candidates reaches the configured scan limit (`filter_limit` in RQL),  
      including candidates rejected by the filter. See [Limit the number of scanned results](#limit-the-number-of-scanned-results).

* **RQL filter comparison semantics**:
    * `=` and `==` use strict equality (`===`); `!=` and `<>` use strict inequality (`!==`).  
      Equality compares both type and value.
    * String comparisons are **case-sensitive**, unlike the default behavior of the RQL `where` clause.  
      This applies to equality and inequality (`==`, `!=`) and range comparisons (`<`, `<=`, `>`, `>=`).  
      Uppercase ASCII letters come before lowercase ASCII letters in character-code order.  
      For example:
        * `filter Address.Country == "usa"` does not match `"USA"`.
        * `filter Name >= "a"` excludes `"Apple"` but includes `"apple"`.

* **The RQL structure illustrates this processing flow**:   
  * `filter` comes after `group by`, `where`, `order by`, and `load`, and before `select` and `include`.  
    `limit` and `filter_limit` come last: `limit` controls paging, and `filter_limit` caps the number of candidates examined.  

  * The outline below shows these clauses together. Optional clauses can be omitted:

    ```sql
    declare function ...         // Optional: define a function to call from 'filter'
    from <collection-name>       // Or: from index "<index-name>"
    group by ...                 // Optional: 'filter' then evaluates the aggregation results
    where ...                    // Optional: narrow the candidate results
    order by ...                 // Optional: sort candidates before filtering
    load ...                     // Optional: load related documents for 'filter'
    filter <condition>           // Evaluated per candidate, without using an index
    select ...                   // Optional: projection
    include ...                  // Optional: send related documents to the client with the results
    limit <offset>, <pageSize>   // Optional: paging
    filter_limit <number>        // Optional: maximum number of candidates to examine
    ```                

* **Query statistics on a non-sharded database**:  
  When an exploration query is executed, the [query statistics](../../../client-api/session/querying/how-to-get-query-statistics.mdx) report:
    * `ScannedResults` counts the candidates actually examined by the filter.
    * `SkippedResults` includes candidates rejected by the filter.  
      It can also include results skipped for other reasons, such as duplicate elimination.

* For sharded databases, see [Filter and sharding](#filter-and-sharding).

<Panel heading="When to use exploration queries">

<ContentFrame>

### Use `filter` when:

* You need a one-time or occasional look at your data, for example during development, debugging, or a support investigation,
  without creating an index solely for that condition.

* Use `filter` when you need to evaluate a condition on fields that aren't indexed.  
  Using `where` for the same condition has these implications:
    * In a static-index query, `where` can use only the index fields.  
      A `where` condition on any other field throws an error.
    * In a dynamic query, a `where` condition on a new field makes RavenDB create an auto-index that includes it.

  Using `filter` avoids these indexing requirements because it evaluates the condition directly against the retrieved results.

* Use `filter` when the required condition cannot be expressed as an ordinary RQL `where` comparison,  
  for example:  
    * Comparing two fields of the same document, for example `filter UnitsInStock < ReorderLevel`.  
      See [Supported operators and limitations](#supported-operators-and-limitations).  
    * Checking a field of a related document. See [Filter by a related document](#filter-by-a-related-document).

* On a **sharded database**, use `filter` when the condition applies to an aggregated value of a Map-Reduce or `group by` query, such as `Count`.
  `filter` evaluates the combined results, while `where` evaluates each shard's partial results and can miss matches.
  See [Filter and sharding](#filter-and-sharding).

</ContentFrame>
<ContentFrame>

### Prefer `where` when:

* The query runs repeatedly and the condition can be evaluated using an index.  
  A dynamic query reuses a suitable auto-index or creates one when needed. Subsequent queries can use that index.

* The condition can be indexed and `filter` would otherwise need to scan a large dataset.  
  The cost of `filter` grows with the number of results it examines.

</ContentFrame>
<ContentFrame>

### `where` vs `filter`:

| Feature               | `where`                                                                                         | `filter`                                                                                                   |
|-----------------------|-------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| **Evaluated against** | An index, for ordinary field conditions                                                         | A document or aggregation result                                                                           |
| **Index usage**       | Uses the queried index.<br/>A dynamic query reuses a suitable auto-index or creates one when needed | No index is used or created for the filter condition                                                       |
| **Work**              | Uses indexed fields to find matches                                                             | Examines results individually, until the page is full, `filter_limit` is reached, or results are exhausted |
| **String comparison** | Case-insensitive by default                                                                     | Case-sensitive                                                                                             |
| **Typical use**       | Recurring queries                                                                               | Ad-hoc exploration or additional filtering logic                                                           |

</ContentFrame>

</Panel>

<Panel heading="Exploration queries vs disabling auto-index creation">

**Exploration queries** use `filter` to evaluate a condition without requiring an index.  
**Disabling auto-index creation** prevents RavenDB from automatically creating new auto-indexes.  
    
The table below compares their purposes and effects on query execution:

| Feature                           | Purpose                                                       | Effect on query execution                                                                                                                                |
|-----------------------------------|---------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Disabling auto-index creation** | Prevent RavenDB from automatically creating new auto-indexes. | **Blocks** a query that would need a new auto-index - the query fails.<br/>The server setting also blocks queries that would use an existing auto-index. |
| **Exploration query** (`filter`)  | Evaluate a filter condition without requiring an index.       | Scans the retrieved results and evaluates the filter condition without using or creating an index for that condition.                                    |

---

### Example

The table below compares queries against the `Products` collection.   
Each product document has a `UnitsInStock` field containing the number of units currently in stock.  
Assume auto-index creation is **disabled** and no existing auto-index covers the UnitsInStock field.   

| Query                                    | Result                                                                    |
|------------------------------------------|---------------------------------------------------------------------------|
| `from Products where UnitsInStock > 10`  | ❌ **Fails**<br/>`where` needs an auto-index, and creating one is disabled.  |
| `from Products filter UnitsInStock > 10` | ✅ **Runs**<br/>`filter` scans the _Products_ documents. No index is needed. |

---

### Use them together

* Disable auto-index creation to protect the database from unplanned indexes,  
  and use `filter` to explore data that no index covers.

* `filter` doesn't exempt the **rest** of the query:  
  Conditions on ordinary document fields in `where`, or sorting by document fields with `order by`,  
  still require an auto-index in a collection query, so the settings still apply.

---

### Where to disable auto-index creation

| Setting                                                                                                                                                                | Applies to                                            | Effect                                                                                |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------|---------------------------------------------------------------------------------------|
| **Studio**:<br/>[Disable creating new Auto-Indexes](../../../studio/database/settings/studio-configuration.mdx#disabling-auto-index-creation-on-studio-queries-or-patches) | Queries and patches run from the Studio, per database | Queries that need a new auto-index fail.<br/>Existing auto-indexes can still be used. |
| **Server**:<br/>[Indexing.DisableQueryOptimizerGeneratedIndexes](../../../server/configuration/indexing-configuration.mdx#indexingdisablequeryoptimizergeneratedindexes)   | All queries and patches, from any client including the Studio.<br/>Server-wide or per database | Queries that need an auto-index fail, even if a suitable one already exists.<br/>Database-level changes take effect after the database is reloaded. |    
<br/>    
    
_Patch-by-query_ and _delete-by-query_ operations do not support `filter`.  
You therefore cannot use `filter` to avoid the auto-index requirements of these operations.  
See [Query and operation restrictions](#query-and-operation-restrictions).  

</Panel>

<Panel heading="Exploration queries by query type">

* You can use `filter` with each of the following query types:
    * **[Full-collection query](../../../querying/overview.mdx#3-query-a-collection---query-full-collection--query-by-id)** -  
      Reads documents directly from a collection, without using a static index or an auto-index.
    * **[Dynamic query](../../../querying/overview.mdx#2-query-a-collection---with-filtering)** -  
      Queries a collection using an auto-index, for example to evaluate `where` conditions or sort by a document field.  
      RavenDB reuses a suitable auto-index or creates one when needed.
    * **[Static-index query](../../../querying/overview.mdx#1-query-an-existing-index)** -  
      Retrieves results using the static index explicitly specified in the query.

* For queries on Map-Reduce indexes and dynamic `group by` queries,  
  `filter` evaluates **aggregation results** rather than individual documents.  
  Learn more in [Filter with a static Map-Reduce index](#filter-with-a-map-reduce-index-query) and [Filter with a dynamic group-by query](#filter-with-a-map-reduce-index-query-dynamic-group-by-query).

* In each case, `filter` applies an **additional condition** to the results retrieved by the query,  
  without using or creating an index for that condition.

### Filter with a dynamic query

* A collection query targets a collection without explicitly specifying an index.  
  RavenDB processes a collection query as a **dynamic query** when it includes a `where` condition on document fields other than just the document ID,
  an `order by` clause that sorts by a document field, or both.  
  It reuses a suitable auto-index or creates one when needed.  
  Learn more in [Query a collection - with filtering](../../../querying/overview.mdx#2-query-a-collection---with-filtering).
    
  Dynamic `group by` queries use an auto Map-Reduce index.  
  See [Filter with a dynamic group-by query](#filter-with-a-map-reduce-index-query-dynamic-group-by-query).

* Narrow the results with `where` first: only results matching that `where` condition are examined by `filter`.  
  The fields referenced in `filter` are **not** added to the auto-index.

* The following query returns full `Company` documents that match both conditions:
    * `where`: `Contact.Title` equals _"Sales Representative"_ (case-insensitive).
    * `filter`: `Address.Country` equals _"Germany"_ (case-sensitive).

### Filter with a static index query
   
* For a static Map index, `where` evaluates its condition against the index-fields,  
  while `filter` evaluates its condition against the original documents.    
  The filter condition can therefore reference document fields that aren't included in the index.    
    
* `filter` cannot see fields that exist only in the index, even if they are stored.  
  For example, if an index computes `StockValue = UnitsInStock * PricePerUnit` and the documents have no `StockValue` field,
  `filter StockValue > 1000` returns no matches without reporting an error.

* For example, create and deploy the following index, which indexes only the product's `Category` field:

    ```csharp
    public class Products_ByCategory : AbstractIndexCreationTask<Product>
    {
        public class IndexEntry
        {
            // The index field
            public string Category { get; set; }
        }
    
        public Products_ByCategory()
        {
            Map = products => from product in products
                              select new IndexEntry
                              {
                                  Category = product.Category
                              };
        }
    }
    ```
    <br/>

* Query the index for beverages (_categories/1-A_), then `filter` the retrieved documents to those whose `PricePerUnit` is greater than 20.  
  `PricePerUnit` is not indexed by this index, so a `where` condition on it would fail.  
    
  Each matching result is a full `Product` document.  
  The query uses the specified static index. No auto-index is created:

<Tabs groupId='languageSyntax'>
<TabItem value="Query" label="Query">
```csharp
List<Product> products = session
    .Query<Products_ByCategory.IndexEntry, Products_ByCategory>()
     // 'Where' is evaluated against the index-field 'Category'
    .Where(x => x.Category == "categories/1-A")
     // Switch the query type to 'Product', so 'Filter' can reference document fields
    .OfType<Product>()
     // 'Filter' is evaluated against each retrieved Product document
    .Filter(p => p.PricePerUnit > 20)
    .ToList();
```
</TabItem>

<Admonition type="info" title="">

#### Why use `OfType<Product>()` before `Filter`?

* The `Query` call uses `Products_ByCategory.IndexEntry` as the query’s initial result type.  
  The `Where` lambda can therefore reference properties defined by `IndexEntry`, such as `Category`.
    
* `OfType<Product>()` switches the query type to `Product` **before** `Filter`,  
  so the `Filter` lambda can reference document fields such as `PricePerUnit`,  
  and the results are returned as `Product`.  
        
  A `Filter` expression that references `PricePerUnit` would not compile before `OfType<Product>()`,  
  because `IndexEntry` does not define that property.
        
* `OfType` changes only the C# type, not the RQL sent to the server.  
  On the server, `filter` evaluates the original documents regardless of the C# type.

</Admonition>

### Filter with a Map-Reduce index query - static Map-Reduce index {/* #filter-with-a-map-reduce-index-query */}

* When querying a Map-Reduce index, the `filter` condition is evaluated against the **aggregation results**,  
  so it references the reduce result fields rather than the original documents.  
  The same applies to dynamic `group by` queries.

* Both this example and the [dynamic group-by query](#filter-with-a-map-reduce-index-query-dynamic-group-by-query) example below use the following C# result class:

    ```csharp
    public class OrdersByCompanyResult
    {
        public string Company { get; set; }
        public int Count { get; set; }
    }
    ```
    <br/>

Create and deploy the following index, which counts orders per company.  
It is a simplified version of _Orders/ByCompany_ from the sample data, containing only `Company` and `Count`:

```csharp
public class Orders_ByCompany : AbstractIndexCreationTask<Order, OrdersByCompanyResult>
{
    public Orders_ByCompany()
    {
        Map = orders => from order in orders
                        select new OrdersByCompanyResult
                        {
                            Company = order.Company,
                            Count = 1
                        };

        Reduce = results => from result in results
                            group result by result.Company into g
                            select new OrdersByCompanyResult
                            {
                                Company = g.Key,
                                Count = g.Sum(x => x.Count)
                            };
    }
}
```
<br/>

The following query returns aggregation results for companies that placed more than 20 orders.  
The query uses `filter` to apply the `Count > 20` condition to the aggregation results.  

<Tabs groupId='languageSyntax'>
<TabItem value="Query" label="Query">

<Admonition type="note" title="">
    
The following applies to dynamic group-by query.    
    
* **RQL: Use the Count field**:    

  In RQL, `count()` in `select` tells RavenDB to include a `Count` field in the auto Map-Reduce index.  
  The `filter` clause reads this field before `select` projects the results.

  For example, with `select Company, count() as NumOrders`:

    | Expression              | Behavior                                                                                                    |
    |-------------------------|-------------------------------------------------------------------------------------------------------------|
    | `filter Count > 20`     | Checks the aggregation count.                                                                               |
    | `filter NumOrders > 20` | Returns no matches without reporting an error<br/>because the projection alias is unavailable during filtering. |
    | `filter count() > 20`   | Throws an error because the RQL `count()` function<br/>is not supported inside `filter`.                        |

* **LINQ: Call Filter before Select**:    

  Call `Filter` after `GroupBy` and before `Select`, using `g.Count()` in the predicate.  
  The client translates `g.Count()` to the aggregation result field `Count`.

  If `Select` renames the count to `NumOrders`, a later `.Filter(x => x.NumOrders > 20)` generates RQL that checks `NumOrders`.  
  This field exists only in the projected output, so the query returns no matches without reporting an error.

</Admonition>

<Panel heading="Limit the number of scanned results">

**How the scan limit works**:

* Set the `limit` argument of `Filter` (LINQ and DocumentQuery), or `filter_limit` in RQL,  
  to specify the **maximum number of candidate results the filter examines**.  
  By default, no `filter_limit` is set. If set, its value must be greater than 0.

* The limit applies to all candidates examined by the filter, whether they pass or fail the condition.  
  Candidates beyond the limit aren't examined or returned, even if they would match.

* When the query includes `where`, `filter_limit` applies to the candidates that match `where`.

---
    
**Scan limit vs page size**:

The **page size** caps the number of matching results returned.  
Filtering can stop before reaching `filter_limit` if the page is full or no more candidates remain.  
Learn more in [Filter and paging](#filter-and-paging).

For example, assume no explicit page size is set, the filter condition is `Country == "USA"`,  
and `filter_limit` is 2. The candidates are examined in the order shown below:

| Candidate result | Country | Examined by filter | Returned |
|------------------|---------|--------------------|----------|
| Employee 1       | USA     | Yes                | Yes      |
| Employee 2       | Poland  | Yes                | No       |
| Employee 3       | USA     | No: limit reached  | No       |

The filter examines two employees, but only **Employee 1** is returned.

* A query can return fewer results, or even no results, while matching candidates exist beyond `filter_limit`.
* Which candidates are examined depends on the order in which the query retrieves them.  
  Use [sorting](#filter-and-sorting) to control this order.

---

**Execution order**:

* Sorting is applied **before filtering**.  
  Use `OrderBy` / `OrderByDescending` in LINQ and DocumentQuery, or `order by` in RQL, to determine the order in which the filter examines candidate results.

### Page through matching results

For document queries on a **non-sharded database**:

* Use `Take` to set the maximum number of matching results per page.
* Use `Skip` to advance past the candidates examined by previous requests.  
  The offset must include both the results returned and the candidates rejected by the filter.

In RQL, use `limit <offset>, <pageSize>` to set the offset and page size.

The following example returns full `Order` documents shipped to the USA, up to 10 per page.  
It assumes the data and candidate order remain unchanged between requests.  
**No `filter_limit` is set**, so each request can examine all remaining candidates if needed.  
The loop stops when a page is empty:

<Tabs groupId='languageSyntax'>
<TabItem value="Query" label="Query">
```csharp
const int pageSize = 10;
int offset = 0;
List<Order> pagedResults;

do
{
    pagedResults = session
        .Query<Order>()
        .Statistics(out QueryStatistics stats)
        .Filter(o => o.ShipTo.Country == "USA")
         // Skip the candidates examined by previous page requests
        .Skip(offset)
         // Return at most 'pageSize' results that passed the filter
        .Take(pageSize)
        .ToList();

    // Process the current page here...

    // Advance the offset by the results returned AND the results the filter rejected
    offset += pagedResults.Count + (int)stats.SkippedResults;
}
while (pagedResults.Count > 0);
```

### Page with a scan limit

For the non-sharded document query above, set `Filter(..., limit: n)` or RQL `filter_limit`  
to cap the number of candidates each request examines **after its offset**, including rejected candidates.  
Filtering can stop earlier if the page is full or no candidates remain.  
See [Limit the number of scanned results](#limit-the-number-of-scanned-results).

The following example returns full `Order` documents shipped to the USA, up to 10 per page,

```csharp
    // Advance the offset by the results returned AND the results the filter rejected
    offset += pagedResults.Count + (int)stats.SkippedResults;
}
```

```csharp
        .DocumentQuery<Order>()
        .Statistics(out stats)
        .Filter(f => f.Equals(o => o.ShipTo.Country, "USA"), limit: scanLimit)
         // Skip the candidates examined by previous page requests
        .Skip(offset)
         // Return at most 'pageSize' results that passed the filter
        .Take(pageSize)
        .ToList();

    // Process the current page here...

    // Advance the offset by the results returned AND the results the filter rejected
    offset += pagedResults.Count + (int)stats.SkippedResults;
}
// Continue if the page is full or the scan limit was reached, even after an empty page.
while (pagedResults.Count == pageSize ||
       stats.ScannedResults == scanLimit);
```

<ContentFrame>

### Document queries

#### Filtering and scan limits
    
* Each shard applies `filter` to its own candidates.  
  When `filter_limit` is set and the paging offset is 0, it caps how many candidates **each shard** examines.  
  The total number examined across all shards can therefore exceed that limit.

* The **orchestrator** (the node coordinating the query) combines the shard results.  
  When `filter_limit` is set, it returns at most the smaller of that limit and the page size.

* **Example**:  
  Assume the first 10 candidate orders on each of three shards match `Freight >= 0`.  
  With `from Orders filter Freight >= 0 filter_limit 10`, each shard examines 10 orders.  
  The combined `ScannedResults` is 30, while the orchestrator returns only 10 results.

---
    
#### Query statistics

* `ScannedResults` is the sum of the candidates examined by the shards.
* `SkippedResults` is reported as 0 and does not include candidates rejected by the filter on the shards.

---
    
#### Paging

For a query that returns full documents and uses `filter` and paging, with or without `where`,  
but without `order by`, `load`, or `filter_limit`, the offset skips matching results in the merged result set.  
Advance it by the number of results returned: `nextOffset = currentOffset + returnedResults.Count`.

---
    
#### Related documents

`load` finds a related document only if it resides on the same shard as the candidate.  
See [Filter by a related document](#filter-by-a-related-document).

</ContentFrame>
<ContentFrame>

### Map-Reduce queries

For queries against static Map-Reduce indexes and dynamic `group by` queries,  
the shards return partial aggregation results **without applying `filter`**.

The orchestrator combines and re-reduces those results, then applies `filter` to the combined aggregation results.  
`filter_limit` caps how many combined aggregation results it examines.

* For these Map-Reduce queries -  
  `ScannedResults` counts the combined aggregation results examined by `filter` on the orchestrator.  
  `SkippedResults` counts those rejected by the filter.

* Use `filter` for conditions on **computed aggregation fields**, such as `Count`.  
  A `where` condition is applied at the shards and can discard partial values before they are combined.

* Use `where` on a **reduce-key (grouping) field**, such as `Company`, to narrow the shard results first.
    
* **Example**:  
  In the [Map-Reduce example](#filter-with-a-map-reduce-index-query), a company with 15 orders on each of two shards has a combined `Count` of 30.  
  `filter Count > 20` includes that combined result.  
  `where Count > 20` discards both partial results before they can be combined.

</ContentFrame>

Learn more in [Sharding: Filtering query results](../../../sharding/querying.mdx#filtering-query-results).

<ContentFrame>

### Supported RQL expressions

The following expressions can be used in an RQL `filter` clause:

| Expression                 | Supported syntax                                                                           |
|----------------------------|------------------------------------------------------------------------------------------- |
| Comparisons                | `=`, `==`, `!=`, `<>`, `<`, `<=`, `>`, `>=`                                                |
| Field-to-field comparisons | Comparing two document fields, such as `UnitsInStock < ReorderLevel`                       |
| Logical expressions        | `and`, `or`, and negation with `and not` or `or not`; parentheses for grouping             |
| Membership                 | `in`                                                                                       |
| Built-in methods           | `startsWith()`, `endsWith()`, `regex()`, `exists()`                                        |
| Document ID                | `id()` for document queries                                                                |
| Related document fields    | Fields from [documents loaded with `load`](#filter-by-a-related-document)                  |
| Custom logic               | Calls to [JavaScript functions defined with `declare`](#filter-with-a-javascript-function) |

---
    
#### Quote string values

Write string literals in quotes, for example `filter Address.Country == "USA"`.  
An unquoted identifier such as `USA` is interpreted as a field name.  
For example, `filter Address.Country == USA` compares `Address.Country` with a field named `USA`,  
which can return no matches without reporting an error.

Missing or misspelled field names can also produce unexpected results without reporting an error.

---

#### Negating the entire condition

Use `true and not (...)`.  
Starting the condition directly with `not` can return no results without reporting an error:
```sql
from Companies
filter true and not (Address.Country == "USA")
```
<br/>
    
The LINQ and DocumentQuery `Filter` APIs handle this automatically. See [API behavior](#api-behavior).

---
    
#### String comparisons

| Expression                                                                              | Case sensitivity                                                   |
|-----------------------------------------------------------------------------------------|--------------------------------------------------------------------|
| RQL `startsWith()` and `endsWith()` helpers                                             | Case-insensitive                                                   |
| RQL `regex()` helper                                                                    | Case-insensitive by default; inline regex options can change this. |
| String equality and `in` comparisons in `filter`                                        | Case-sensitive                                                     |
| JavaScript's native `someString.startsWith(...)` and `someString.endsWith(...)` methods | Case-sensitive                                                     |

For strict equality and string ordering rules, see [How exploration queries work](#how-exploration-queries-work).    

</ContentFrame>

### Unsupported RQL expressions

These restrictions also apply when using `RawQuery` or `AsyncRawQuery`:

* **Index-based methods**:  
  `search()`, `boost()`, `lucene()`, `exact()`, `moreLikeThis()`, spatial methods, and vector search   
  cannot be used inside a filter condition.

* **Arithmetic**:  
  Expressions such as `UnitsInStock * PricePerUnit` cannot be used directly in an RQL `filter` condition.  
  Compute the value in a [declared function](#filter-with-a-javascript-function) and compare its result.

* **`between`**:  
  This operator is not supported in a filter condition and can return no results without reporting an error.  
  Use two comparisons instead:
  ```sql
  from Products
  filter PricePerUnit >= 10 and PricePerUnit <= 20
  ```

* **`now()` and `today()`**:  
  These functions cannot be used inside a filter condition.  
  Compare against an explicit date-time value instead.
  Learn more in [Filter by date and time: Restrictions](../../../querying/filtering-query-results/filter-by-date-and-time.mdx#restrictions).

</ContentFrame>

### LINQ and DocumentQuery APIs

* The LINQ, DocumentQuery, and AsyncDocumentQuery `Filter` APIs support comparisons and logical expressions.  
  DocumentQuery and AsyncDocumentQuery use the `IFilterFactory` methods listed in [Syntax](#syntax).

* Use `RawQuery` or `AsyncRawQuery` for supported RQL features that these `Filter` APIs do not expose.

* `IFilterFactory<T>` comparison methods compare a field with a value.  
  For example, `f.LessThan("UnitsInStock", "ReorderLevel")` compares `UnitsInStock` with the literal string `"ReorderLevel"`.  
  To compare two document fields, use `RawQuery` or `AsyncRawQuery` with a condition such as `filter UnitsInStock < ReorderLevel`.

---
    
#### LINQ limitations

* **Unsupported methods and field comparisons**:  
  LINQ `Filter` does not support methods such as `StartsWith`, `EndsWith`, `In`, `Regex.IsMatch`,  
  `ContainsAny`, `ContainsAll`, or `string.Contains`, or comparisons between two document fields  
  (for example, `p.UnitsInStock < p.ReorderLevel`). These expressions throw during query translation.  
    
  To compare two document fields, use `RawQuery` or `AsyncRawQuery` with a condition such as `filter UnitsInStock < ReorderLevel`.  
  For supported RQL helpers or custom logic, use `RawQuery` or `AsyncRawQuery`,  
  optionally with a [declared JavaScript function](#filter-with-a-javascript-function).

* **`string.Length`**:  
  LINQ `Filter` does not translate `string.Length` to JavaScript's `length` property.  
  For example, `Filter(c => c.Name.Length > 30)` generates `filter Name.Length > $p0`,  
  so this comparison matches no results without reporting an error.  
  Use `filter Name.length > 30` with `RawQuery` or `AsyncRawQuery`.

---
    
<Admonition type="note" title="">

#### API behavior

* Calling `.Search()` on the query adds a `where search(...)` condition; it does not add a filter condition.

* Calling LINQ `Filter` more than once combines the conditions with `and`.

* Negation in `Filter` is handled by the client,  
  so the RQL pitfall described in [Negating the entire condition](#negating-the-entire-condition) does not apply.

* For a negated comparison such as `Filter(p => !(p.PricePerUnit > 10))`,  
  LINQ generates `filter (true and not (PricePerUnit > $p0))`.

* In _DocumentQuery_ and _AsyncDocumentQuery_, the RQL generated by starting the condition with `Not()`  
  depends on what follows `Not()`:

  | DocumentQuery                                   | Generated RQL                                            |
  |-------------------------------------------------|----------------------------------------------------------|
  | `f.Not().Equals("Address.Country", "USA")`      | `filter Address.Country != $p0`                          |
  | `f.Not().GreaterThan("PricePerUnit", 10)`       | `filter exists(PricePerUnit) and not PricePerUnit > $p0` |
  | `f.Not().OpenSubclause() ... .CloseSubclause()` | `filter true and not (...)`                              |

  The `exists(...)` form excludes documents that don't have the field.

</Admonition>

### Query and operation restrictions

The following queries and operations cannot include a `filter` clause:

* **Faceted search**:  
  A [faceted search](../../../indexes/querying/faceted-search.mdx) query with `filter` throws an `InvalidQueryException`.

* **Vector search**:  
  A query that uses `vector.search()` in `where` cannot also include `filter`.

* **Patch by query and delete by query**:  
  Use `where` to select documents for [patch by query](../../../documents/patching-documents/patch-multiple-documents/client-api.mdx)
  and [delete by query](../../../client-api/operations/common/delete-by-query.mdx) operations.

### Filter parameters

| Parameter     | Type                                   | Description                                                                                                                   |
| ------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **source**    | `IRavenQueryable<T>` / `IQueryable<T>` | RavenDB LINQ query to which the filter is added.                                                                              |
| **predicate** | `Expression<Func<T, bool>>`            | LINQ expression translated into a filter condition that the server evaluates for each examined candidate.                     |
| **builder**   | `Action<IFilterFactory<T>>`            | Constructs the filter condition for DocumentQuery, AsyncDocumentQuery, or a group-by query.                                   |
| **limit**     | `int`                                  | Maximum number of candidate results examined, including rejected candidates. Must be greater than 0.<br/>Default: `int.MaxValue`. |

<Admonition type="note" title="">

#### Scan limit

`limit` corresponds to RQL's `filter_limit`.  
**It does not set the maximum number of matching results returned.**

The default value, `int.MaxValue`, sends no `filter_limit`.  
Scanning can still stop when the page is full or candidates are exhausted.

Learn more in [Limit the number of scanned results](#limit-the-number-of-scanned-results) and [Filter and paging](#filter-and-paging).  
For sharded queries, see [Filter and sharding](#filter-and-sharding).

### Filter builder methods

The `IFilterFactory<T>` interface provides the following comparison, logical, and grouping methods:

```csharp
public interface IFilterFactory<T>
{
    // Equality
    IFilterFactory<T> Equals(string fieldName, object value);
    IFilterFactory<T> Equals<TValue>(Expression<Func<T, object>> propertySelector,
        TValue value);

    IFilterFactory<T> NotEquals(string fieldName, object value);
    IFilterFactory<T> NotEquals<TValue>(Expression<Func<T, object>> propertySelector,
        TValue value);

    // Comparison
    IFilterFactory<T> GreaterThan(string fieldName, object value);
    IFilterFactory<T> GreaterThan<TValue>(Expression<Func<T, object>> propertySelector,
        TValue value);

    IFilterFactory<T> GreaterThanOrEqual(string fieldName, object value);
    IFilterFactory<T> GreaterThanOrEqual<TValue>(Expression<Func<T, object>> propertySelector,
        TValue value);

    IFilterFactory<T> LessThan(string fieldName, object value);
    IFilterFactory<T> LessThan<TValue>(Expression<Func<T, object>> propertySelector,
        TValue value);

    IFilterFactory<T> LessThanOrEqual(string fieldName, object value);
    IFilterFactory<T> LessThanOrEqual<TValue>(Expression<Func<T, object>> propertySelector,
        TValue value);

    // Logical operators and grouping
    IFilterFactory<T> AndAlso();
    IFilterFactory<T> OrElse();
    IFilterFactory<T> Not();
    IFilterFactory<T> OpenSubclause();
    IFilterFactory<T> CloseSubclause();

    // Overloads that accept 'MethodCall' and 'WhereParams' are omitted for brevity
}
```

#### Builder method parameters

| Parameter            | Type                          | Description                                                                                                         |
| -------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **fieldName**        | `string`                      | Document field or reduce result field to compare. Use a dotted path for nested fields, such as `"Address.Country"`. |
| **propertySelector** | `Expression<Func<T, object>>` | Lambda expression selecting the field to compare.                                                                   |
| **value**            | `object` / `TValue`           | Value to compare against.                                                                                           |

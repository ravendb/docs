* Use the **Patch** operation to update selected parts of a document without requiring the client to load, modify,  
  and save the full document.  
  
* The patch is sent in a single request and applied atomically by the server in a single write [transaction](../../../../client-api/faq/transaction-support.mdx).

### Session API

The `session.advanced` API provides the following methods for common single-document patch operations:

* `patch`
* `patch_array`
* `patch_object`
* `add_or_patch`
* `add_or_patch_array`
* `increment`
* `add_or_increment`

<ContentFrame>

#### Example: Modify a single field

```python
# Modify FirstName to Robert       
session.advanced.patch("employees/1-A", "FirstName", "Robert")

session.save_changes()
```

</ContentFrame>

---    
    
**Patch format**:      
Each method generates a JavaScript patch command from a predefined script template.  
The Python client does not provide an API for sending RFC 6902 JSON Patch commands.  
   
**Saving session patches**:    
Calls to these methods are queued in the [session](../../../../client-api/session/what-is-a-session-and-how-does-it-work.mdx)
and sent to the server only when [save_changes](../../../../client-api/session/saving-changes.mdx) is called.  
`save_changes()` sends the patch commands together with all other changes tracked by the session -  
including stored, modified, and deleted documents - as a single batch in one HTTP request.    
    
**Missing documents**:    
If the target document does not exist, session-generated `patch`, `patch_array`, `patch_object`,  
and `increment` commands make no changes, and `save_changes()` does not throw.  
Use `add_or_patch`, `add_or_patch_array`, or `add_or_increment` when a missing document should be created.      

**Transaction guarantees**:  
The server executes the entire `save_changes` batch in one ACID transaction.  
If the server cannot execute any command in the batch, for example because of a patch error or a concurrency conflict, `save_changes()` raises an exception.  
The server rolls back the transaction, and none of the changes in the batch are persisted.  
When `save_changes()` completes successfully, the entire batch has been persisted.  

**Optimistic concurrency**:  
Patch commands generated by these `session.advanced` patch methods carry no change vector,  
even when [optimistic concurrency](../../../../client-api/session/configuration/how-to-enable-optimistic-concurrency.mdx) is enabled.  
Consequently, these generated patch commands are not rejected merely because the target document changed after the patch was queued.  
    
Another command in the batch - such as a stored document or an explicitly deferred
[PatchCommandData](#session-api-using-defer-syntax) that supplies a change vector - can still fail with a concurrency conflict.

**Merging patches for the same document**:    
While a patch command is already queued for a document, a subsequent `patch`, `patch_array`, `patch_object`,  
or `increment` call for that same document is merged into the pending command rather than queued as a new one.  
The scripts are concatenated in call order and their parameter values are combined,  
so all the changes are applied by a single script in the same transaction.  
Reversing the call order can still change the final value when two calls modify the same field.

**Removals that target missing elements**:    
A `remove_at` with a non-negative index at or beyond the array length, or a `remove` of a key that is not  
present in an object, is applied as a JavaScript no-op. No exception is thrown, and the other changes  
in the batch are still applied.

**Negative array indexes**:    
A negative index is not out of range.
`remove_at` generates `splice(index, 1)`, and JavaScript `splice` treats a negative index as an offset from the end of the array,
so `remove_at(-N)` removes the Nth item from the end and `remove_at(-1)` removes the last item.
Exactly one item is removed in either case.

**Patching a document that is loaded in the same session**:    
If the session tracks the target document and considers it modified, `save_changes()` raises  
`Cannot perform save because document <id> has been modified by the session and is also taking part in deferred PATCH command`.  
This can happen even when you did not edit the entity, for example when the document was written by another client,  
and it applies whether you pass the document ID or the entity.  
Either queue the patch from a session that has not loaded the document,  
or call `session.advanced.ignore_changes_for(entity)` before queueing it.  
`ignore_changes_for` also discards in-memory edits made to that entity,  
so use it only when the patch is the only change you want persisted for that document.

</Admonition>

### Session API using Defer

* Use `session.advanced.defer` to queue a low-level patch command instead of using the  
  `session.advanced` patch methods. Defining the command yourself gives you full control over the  
  patch script and access to options the wrapper methods do not expose.

* Create a `PatchRequest` containing a JavaScript script and optional parameter values,  
  then pass it in a `PatchCommandData` for the document you want to patch.  
  `PatchCommandData` also accepts an optional `change_vector`, which enforces optimistic concurrency  
  for the patch, and an optional `patch_if_missing` script, which runs when the document does not exist.  
  The `session.advanced.patch` methods expose neither option.
    
  `PatchCommandData` also has a `create_if_missing` property,  
  which supplies a full document to store when the target document does not exist, instead of a script to run.    

* `defer` adds the `PatchCommandData` to the session's unit of work.  
  The command is sent to the server only when `save_changes()` is called,  
  together with the session's other pending changes in a single request and transaction.

<ContentFrame>

#### Example: Modify a single field

```python
# Modify FirstName to Robert     
patch_request = PatchRequest()
patch_request.script = "this.FirstName = args.FirstName;"
patch_request.values = {"FirstName": "Robert"}

session.advanced.defer(PatchCommandData(
    "employees/1-A",  # key
    None,             # change_vector
    patch_request,    # patch
    None))            # patch_if_missing

session.save_changes()
```

</ContentFrame>

**Patch failures**:  
If the server cannot compile or execute the deferred JavaScript patch script, `save_changes()` raises an exception.  
The server rolls back the entire session batch, so neither partial changes from the patch nor any other changes in the batch are persisted.

**Deferred and immediate execution**:    
`PatchCommandData` derives from `CommandData`, which represents command data included in a batch;  
it is not a [RavenCommand](../../../../client-api/commands/overview.mdx) that can be executed directly through a request executor.  
To send a single-document patch without waiting for `save_changes()`, use the [Operations API](#operations-api) described below.

**Mixing deferred and wrapper-method patches**:    
Avoid calling `session.advanced.patch` after deferring a `PatchCommandData` for the same document in the same session.
The patch call is merged into the deferred command, but the merge does not preserve the deferred command's
`change_vector`, `patch_if_missing` script, or `create_if_missing` document.  
    
To keep the changes in one transaction, express them all in the deferred script;  
otherwise, send them in separate `save_changes()` calls or sessions.

</Admonition>

### Operations API

* **Creating and executing the operation**:  
  Use the [Operations API](../../../../client-api/operations/what-are-operations.mdx) to patch a single document directly through the document store,  
  without opening a session.

  Create a `PatchRequest` containing a JavaScript script and optional parameter values, then pass it to `PatchOperation`
  together with the document ID and any optional concurrency or missing-document settings.

  Execute the operation with `store.operations.send()`. Unlike a deferred session command,  
  the patch is sent to the server immediately in its own HTTP request and its own transaction,  
  and does not wait for `save_changes()`. Separate operations are therefore not applied atomically together.

<ContentFrame>

#### Example: Modify a single field

```python
# Modify FirstName to Robert     
patch_request = PatchRequest()
patch_request.script = "this.FirstName = args.FirstName;"
patch_request.values = {"FirstName": "Robert"}

store.operations.send(PatchOperation(
    "employees/1-A",  # key
    None,             # change_vector
    patch_request))   # patch
```

</ContentFrame>

* **Patch failures**:  
  If the server cannot compile or execute the JavaScript patch script, `store.operations.send(...)` raises an exception instead of returning a `PatchResult`.  
  The server rolls back the operation's transaction, and no partial changes from the operation are persisted.

* **Patch status**:  
  `send` returns a `PatchResult` object that holds the patch `status` and the resulting `modified_document`.  
  If no document with the given ID is found and no `patch_if_missing` script was provided,  
  the server reports that the document does not exist, `send` returns `None`, and no exception is thrown.  
      
  To get the status itself in that case, use `store.operations.send_patch_operation`,  
  which returns only a `PatchStatus` and reports a missing document as `PatchStatus.DOCUMENT_DOES_NOT_EXIST`.  

  If `skip_patch_if_change_vector_mismatch` is `True`, a change-vector mismatch skips the patch and is reported  
  as `PatchStatus.NOT_MODIFIED`. With the default `False`, a mismatch throws a `ConcurrencyException` instead.

* **Returning the document**:  
  To have the returned document deserialized into one of your own classes,  
  use `store.operations.send_patch_operation_with_entity_class()` and pass the class as the first argument.  
  It returns a `PatchOperation.Result` object whose `document` property holds the deserialized entity.  
  Plain `send` returns the document as a dictionary in `PatchResult.modified_document`.
        
  The document is returned when the status is `PatchStatus.CREATED` or `PatchStatus.PATCHED`.  
  It is also populated when the patch executes but makes no changes and returns `PatchStatus.NOT_MODIFIED`.  
  It is not set when the target document does not exist and no `patch_if_missing` script was supplied,  
  or when the server skips the patch.  
        
  See [Operations API syntax](#operations-api-syntax) for the method signatures and the result properties.

</Admonition>

### Session API using Defer syntax

The non-typed Session API for patches uses the `session.advanced.defer` function which allows registering one or more commands.  
One of the possible commands is the `PatchCommandData`, describing single document patch command.  
The patch request will be sent to the server only when calling `save_changes`, this way it's possible to perform multiple operations in one request to the server.  

#### `session.advanced.defer`
        
<TabItem value="patch_defer_in_session" label="patch_defer_in_session">
```python
defer(*commands)
```
</TabItem>

| Parameter    | Type          | Description                                                                                                |
| ------------ | ------------- | ---------------------------------------------------------------------------------------------------------- |
| **commands** | `CommandData` | List of commands that will be executed on the server.<br/>Use the `PatchCommandData` command for patching. |

<Admonition type="info" title="">

#### PatchCommandData

<TabItem value="class_PatchCommandData" label="class_PatchCommandData">
```python
PatchCommandData(key, change_vector, patch, patch_if_missing=None)
```
</TabItem>

| Constructor          | Type           | Description                                                                                                                              |
| -------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **key**              | `str`          | ID of the document to be patched.                                                                                                        |
| **change_vector**    | `str`          | [Can be None] Change vector of the document to be patched, used to verify that the document was not changed before the patch reached it.  |
| **patch**            | `PatchRequest` | Patch request to be performed on the document.                                                                                           |
| **patch_if_missing** | `PatchRequest` | [Can be None] Patch request to be performed if no document with the given ID was found.                                                   |

| Property               | Type   | Description                                                                                               |
| ---------------------- | ------ | --------------------------------------------------------------------------------------------------------- |
| **create_if_missing**  | `dict` | [Can be None] Document to create if no document with the given ID was found, instead of running a script.  |

</Admonition>

<Admonition type="info" title="">

#### PatchRequest

We highly recommend using scripts with parameters. This allows RavenDB to cache scripts and boost performance. 
Parameters can be accessed in the script through the `args` object and passed using PatchRequest's "values" property.

| Property   | Type                   | Description                                                                                                                        |
| ---------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **script** | `str`                  | The patching script, written in JavaScript.                                                                                        |
| **values** | `Dict[str, object]`    | Parameters to be passed to the script.<br/>Each parameter is accessed in the script as a property of `args`, e.g. `args.FirstName`. |

* Both properties can also be passed to the constructor: `PatchRequest(script, values)`.  
  For a script that needs no parameters, `PatchRequest.for_script(script)` creates the request in a single call.

</Admonition>

### Operations API syntax

An operations interface that exposes the full functionality and allows performing ad-hoc patch operations without creating a session.  

The methods are exposed by the `OperationExecutor`, which is available as `store.operations`.  

<TabItem value="patch_in_store" label="patch_in_store">
```python
# Returns a PatchResult
store.operations.send(patch_operation)

store.operations.send(patch_operation, session_info)

# Returns the PatchStatus alone
store.operations.send_patch_operation(patch_operation, None)

store.operations.send_patch_operation(patch_operation, session_info)

# Pass an entity class to deserialize the returned document into your own class
store.operations.send_patch_operation_with_entity_class(entity_class, patch_operation)

store.operations.send_patch_operation_with_entity_class(entity_class, patch_operation, session_info)
```
</TabItem>

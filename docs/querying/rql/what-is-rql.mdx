<Admonition type="note" title="">

* **What is RQL**:  
  Queries in RavenDB use a SQL-like language called **RQL** (Raven Query Language).  
  RQL exposes the RavenDB query pipeline in a straightforward, accessible manner that is easy to interact with.    
  The RQL query structure reflects the order of operations performed by the RavenDB server when serving a query.   

* **High-level queries are translated to RQL**:  
  Any query written using high-level Session methods (`Query`, `DocumentQuery`) will be translated by the client into RQL  
  before being sent to the server for execution.
  Learn more about querying from the session in this [Query Overview](../../querying/overview.mdx).    

* **Writing RQL directly:**  
  A query can be written directly in RQL by either:  
  * Using the session's [RawQuery](../../querying/overview.mdx#session-advanced-rawquery) method in the Client API.  
  * Writing a query in the [Query view](../../studio/database/queries/query-view.mdx) in Studio, where [RQL code assistance](../../querying/rql/rql-code-assistance.mdx) is available.

* **RQL keywords are case-insensitive**:  
  For example, `SELECT`, `select`, and `Select` are equivalent.

<Panel heading="The query pipeline">

The query pipeline in RavenDB includes the following main stages:  

1. **Detect query source** ([`from`](../../querying/rql/what-is-rql.mdx#from))

   * Based on your query, RavenDB will determine the appropriate data source from which to retrieve results.           
   * The following options are available:     
     * `from index` - Explicitly specify which index to use.   
     * `from collection` - Specify the collection to query.  
       RavenDB will decide which index will be used depending on the query criteria.
   * Note: all queries in RavenDB use an index to provide results, even when you don't specify one.  
     Learn more about these **query scenarios** in this [Query Overview](../../querying/overview.mdx#queries-always-provide-results-using-an-index).

2. **Filter the data** ([`where`](../../querying/rql/what-is-rql.mdx#where))  
   * The index is scanned for records that match the query predicate. 

3. **Sort results** ([`order by`](../../querying/rql/what-is-rql.mdx#order-by)) 
   * Query results can be sorted.  
     For example, you can order by a field value, by the resulting documents' score, by random ordering, etc.

4. **Filter the retrieved results** ([`filter`](../../querying/rql/what-is-rql.mdx#filter))
   * Optionally, an [exploration query](../../querying/filtering-query-results/exploration-queries.mdx) applies an additional condition to the results retrieved by the previous stages.  
     The server examines these results one by one and keeps those that match the `filter` condition.  
     No index is used or created for this condition.
   * The condition can reference related documents loaded with [`load`](../../querying/rql/what-is-rql.mdx#load).
   * On a non-sharded database, filtering stops when the requested page is full, when no candidates remain,  
     or when the number of examined candidates reaches [`filter_limit`](../../querying/filtering-query-results/exploration-queries.mdx#limit-the-number-of-scanned-results).
   * For sharded document queries with a paging offset of 0, `filter_limit` applies to each shard separately,  
     so the total number examined can exceed that limit.
     See [Filter and sharding](../../querying/filtering-query-results/exploration-queries.mdx#filter-and-sharding).

5. **Limit results** ([`limit`](../../querying/rql/what-is-rql.mdx#limit))
   * You can specify the number of results you want to get back from the query  
     and the number of results you want to skip.
   * For document queries on a non-sharded database that use `filter`, the offset skips candidate results **before** filtering;
     the page size limits the number of matching results returned.
   * Learn how paging interacts with `filter` in [Filter and paging](../../querying/filtering-query-results/exploration-queries.mdx#filter-and-paging).

6. **Project results** ([`select`](../../querying/rql/what-is-rql.mdx#select)) 
   * [Projections](../../indexes/querying/projections.mdx) are specified when you need to retrieve only specific document fields, instead of the whole full document.
     This reduces the amount of data sent over the network and is useful when only partial data is needed.
     When projections are Not defined on the query - then the full document content is retrieved from the document storage.

   * Projections are applied after results have been filtered, sorted, and paged, before related documents are included.  
     This means that the projection doesn't apply to all the documents in the database,  
     only to the results that are actually returned.

   * Data can be loaded ([`load`](../../querying/rql/what-is-rql.mdx#load)) from related documents to be used in the projected fields.  
   
   * For each record, the server extracts the requested field:  
     If a field is stored in the index - the server will fetch it from the index.  
     If a field is Not stored in the index - the server will fetch it from the document storage.  

7. **Include related documents** ([`include`](../../querying/rql/what-is-rql.mdx#include))
   * [Related documents](../../client-api/how-to/handle-document-relationships.mdx#includes) referenced by the returned query results are retrieved and sent to the client  
     along with those results, reducing the need to do another network round trip to the database when accessing the included documents.
   * When a projection is used, include paths are evaluated against the projected fields.

8. **Return results** to the client.

</Panel>

## `declare`

You can use the `declare` keyword to create a JavaScript function that can then be called from a `select` clause when using a projection,
or from a [`filter`](../../querying/rql/what-is-rql.mdx#filter) clause. Declared functions cannot be called from `where`.  
JavaScript functions add flexibility to your queries as they can be used to manipulate and format retrieved results.  

```sql
// Declare a JavaScript function 
declare function output(employee) {
    // Format the value that will be returned in the projected field 'FullName'
    var formatName = function(x){ return x.FirstName + " " + x.LastName; };
    return { FullName : formatName(employee) };
}

// Query with projection calling the 'output' JavaScript function
from Employees as employee select output(employee)
```
<br/>

Values are returned from a declared JavaScript function as a set of values rather than in a nested array to ease the projection of retrieved values.
See an example for this usage [here](../../document-extensions/timeseries/querying/overview-and-syntax.mdx#combine-time-series-and-custom-functions).  

A declared function can encapsulate filtering logic for use in `filter`,  
such as the following comparison between two fields of the same document:

```sql
// Declare a JavaScript function that compares two fields of the same document
declare function needsReorder(product) {
    return product.UnitsInStock < product.ReorderLevel;
}

// Call it from 'filter' - it must return 'true' for a product to be included
from Products as p
filter needsReorder(p)
```
<br/>

Learn more in [Filter with a JavaScript function](../../querying/filtering-query-results/exploration-queries.mdx#filter-with-a-javascript-function).

## `from`

The keyword `from` is used to determine the source data that will be used when the query is executed.  
The following options are available:
    
<ContentFrame>

#### Query a specific collection: &nbsp;&nbsp; `from <collection-name>`

```sql
// Full collection query 
// Data source: The raw collection documents (Auto-index is Not created)
from "Employees"
```
<br/>

```sql
// Collection query - by ID 
// Data source: The raw collection documents (Auto-index is Not created)
from "Employees" where id() = "employees/1-A"
```
<br/>

```sql
// Dynamic query - with filtering
// Data source: Auto-index (server uses an existing auto-index or creates a new one)
from "Employees" where FirstName = "Laura"
```

</ContentFrame>

<ContentFrame>

#### Query all documents: &nbsp;&nbsp; `from @all_docs`

```sql
// All collections query
// Data source: All raw collections (Auto-index is Not created)
from @all_docs
```
<br/>

```sql
// Dynamic query - with filtering 
// Data source: Auto-index (server uses an existing auto-index or creates a new one)
from @all_docs where FirstName = "Laura"
```

</ContentFrame>

<ContentFrame>

#### Query an index: &nbsp;&nbsp; `from index <index-name>`

```sql
// Index query
// Data source: The specified index
from index "Employees/ByFirstName"
```
<br/>

```sql
// Index query - with filtering
// Data source: The specified index
from index "Employees/ByFirstName" where FirstName = "Laura"
```

</ContentFrame>

## `where`

Use the `where` keyword with various operators to filter chosen documents from the final result-set.  
    
<ContentFrame>

#### Operator: &nbsp;&nbsp; `>=`, `<=`, `<>`, `!=`, `<`, `>`, `=`, `==`

These basic operators can be used with all value types, including 'numbers' and 'strings'.  
For example, you can return every document from the [Companies collection](../../client-api/faq/what-is-a-collection.mdx) 
whose _field value_ **=** _a given input_.  

```sql
from "Companies"
where Name == "The Big Cheese" // Can use either '=' or '==' 
```
<br/>

Filtering on **nested properties** is also supported.  
So in order to return all companies from 'Albuquerque' we need to execute following query:  

```sql
from "Companies"
where Address.City = "Albuquerque"
```

</ContentFrame>
    
<ContentFrame>

#### Operator: &nbsp;&nbsp; `between`

The operator `between` returns results inclusively, and the type of border values used must match.  
It works on both 'numbers' and 'strings' and can be substituted with the `>=` and `<=` operators.

```sql
from "Products" 
where PricePerUnit between 10.5 and 13.0 // Using between
```
<br/>

```sql
from "Products" 
where PricePerUnit >= 10.5 and PricePerUnit <= 13.0 // Using >= and <=
```

</ContentFrame>
    
<ContentFrame>

#### Operator: &nbsp;&nbsp; `in`

The `in` operator evaluates a field against a list of values.  
It will return results if the field matches **any** of the items in that list.    

```sql
from "Companies" 
where Name in ("The Big Cheese", "Unknown company name")
```
<br/>

```sql
from "Orders" 
where Lines[].ProductName in ("Chang", "Spegesild", "Unknown product name") 
```

---

**To negate an `in` condition**, use the `NOT` operator.  
In RQL, `NOT` cannot start a `where` clause; it must follow a **valid preceding expression.**

To ensure accuracy, especially when fields might be missing from some documents,  
use `exists(fieldName)` as the anchor:
    
```sql
from "Companies" 
where exists(Name) and NOT Name in ("The Big Cheese", "The Cracker Box")
```
<br/>

**Note:**  
Avoid using `where true` or an `exists()` check on a *different* field.  
If a document is missing the field you're filtering on, these anchors may return unexpected results.

</ContentFrame>
    
<ContentFrame>

#### Operator: &nbsp;&nbsp; `all in`

This operator checks if **all** passes values are matching a given field.  
Due to its mechanics, it is only useful when used on array fields.

The following query will yield no results in contrast to the `in` operator.

```sql
from "Orders" 
where Lines[].ProductName all in ("Chang", "Spegesild", "Unknown product name")
```
<br/>

Removing 'Unknown product name' will return only orders that contain products with both  
'Chang' and 'Spegesild' names.

```sql
from "Orders" 
where Lines[].ProductName all in ("Chang", "Spegesild") 
```

</ContentFrame>
    
<ContentFrame>

#### Binary operators: &nbsp;&nbsp; `AND`, `OR`, `NOT`

Binary operators can be used to build more complex statements.  
The `NOT` operator can only be used with one of the other binary operators creating `OR NOT` or `AND NOT` ones.

Learn more about combining filter conditions with these operators in [Use logical operators](../../querying/filtering-query-results/use-logical-operators.mdx).

```sql
from "Companies"
where Name = "The Big Cheese" OR Name = "Richter Supermarkt"
```
<br/>

```sql
from "Orders"
where Freight > 500 AND ShippedAt > '1998-01-01'
```
<br/>

```sql
from "Orders"
where Freight > 500 AND ShippedAt > '1998-01-01' AND NOT Freight = 830.75
```

</ContentFrame>
    
<ContentFrame>
    
#### Methods: &nbsp;&nbsp; `today()`, `now()` 

Use `today()` and `now()` to compare date/time fields with the current server date or current server time.  
Learn more in [Filter by date and time](../../querying/filtering-query-results/filter-by-date-and-time.mdx).    

```sql    
// Find orders that were shipped before the current date    
from "Orders"
where ShippedAt < today()
```    
<br/>
    
```sql
// Find orders that are required at or after the current date and time
from "Orders"
where RequireAt >= now()
```    
    
</ContentFrame>
    
<ContentFrame>
    
#### Method: &nbsp;&nbsp; `when()`

Use `when(condition, predicate)` to conditionally apply a predicate in a `where` clause.  
The `condition` is evaluated server-side against query parameters, not document fields, before documents are matched.
When the condition is `true`, the predicate is applied; when it is `false`, the predicate is skipped.

This is useful for optional search criteria, without building different query strings on the client.

This feature is available in RQL only - it is not exposed through LINQ queries or DocumentQuery.  
Learn more in [Conditional filtering](../../querying/filtering-query-results/conditional-filtering.mdx).

```sql
// Apply the Country predicate only when the $country parameter is non-null
from "Employees"
where when($country != null, Address.Country == $country)
```    
    
</ContentFrame>    

<ContentFrame>

#### Subclauses: &nbsp;&nbsp; `(`, `)`

Subclauses can be used along with binary operators to build even more complex logical statements.  
See [Group conditions to control precedence](../../querying/filtering-query-results/use-logical-operators.mdx#group-conditions-to-control-precedence).

</ContentFrame>

## `filter`

Use `filter` to apply an additional condition to the results retrieved by the query, without using or creating an index for that condition.
The server examines the retrieved results one by one, so `filter` is intended for ad-hoc exploration rather than for recurring queries.
Learn more in [Exploration queries](../../querying/filtering-query-results/exploration-queries.mdx).

For document queries, `filter` evaluates document fields.  
For Map-Reduce index queries and dynamic `group by` queries, it evaluates aggregation results.

For example, on a non-sharded database:

```sql
from Orders
where Freight > 100             // Evaluated using an index
filter ShipTo.Country == "UK"   // Evaluated on each retrieved document, without an index
filter_limit 50                 // Optional: examine at most 50 candidates
```
<br/>

* `filter` comes after `group by`, `where`, `order by`, and `load`, and before `select`, `include`, and `limit`.  
  You can place `filter_limit` at the end, as shown above, or before `limit`.

* In sharded document queries with a paging offset of 0, `filter_limit` caps the number of candidates examined **per shard**,
  so the total number examined across all shards can exceed that limit.
  See [Filter and sharding](../../querying/filtering-query-results/exploration-queries.mdx#filter-and-sharding).

* A `filter` condition can use comparisons, `and`, `or`, negation with `and not` or `or not`, `in`,  
  the `startsWith()`, `endsWith()`, `regex()`, `exists()`, and `id()` methods,  
  fields of documents loaded with [`load`](../../querying/rql/what-is-rql.mdx#load), and calls to functions defined with [`declare`](../../querying/rql/what-is-rql.mdx#declare).  

  Only some `where` operators and methods are supported in `filter`.  
  Index-based methods such as `search()`, as well as `now()` and `today()`, cannot be used in `filter`.  
  The `between` operator is also unsupported and can return no results without an error; use `>=` and `<=` instead.  
  See [Supported operators and limitations](../../querying/filtering-query-results/exploration-queries.mdx#supported-operators-and-limitations).

* String equality in `filter` is case-sensitive, unlike the default behavior of `where`.

## `order by`

Use `order by` to sort the query results by one or more fields.  
Learn more about sorting in the [Sort query results](../../querying/sorting-query-results/sort-query-results.mdx) article.
    
RQL syntax:  
    
```sql
ORDER BY <expression> [AS <type>] [ASC | DESC] [NULLS FIRST | NULLS LAST]
```
<br/>
    
By default, results are sorted in ascending order.

```sql
from "Employees"
order by FirstName // ascending order
```
<br/>
    
To specify the sort direction, add `asc`, `ascending`, `desc`, or `descending`.

```sql
from "Employees"
order by FirstName desc // descending order
```
<br/>

You can also specify the sort type by adding `as <type>`.    
```sql
from "Products"
order by UnitsInStock as long desc
```
<br/>

Use `nulls first` or `nulls last` to control where matching documents with `null` or missing values in the sorted field will appear in the query results.
This is supported only by the [Corax](../../indexes/search-engine/corax.mdx) search engine.     
    
The `nulls first` and `nulls last` options are absolute.
They place those documents before or after matching documents with non-null values, regardless of whether the query sorts in ascending or descending order:

  * `nulls first` places those documents **before** matching documents with non-null values.
  * `nulls last` places those documents **after** matching documents with non-null values.   
    
```sql
// Place documents whose ReportsTo field is null (or missing) at the top of the results
from "Employees"
order by ReportsTo nulls first
```
<br/>

```sql
// Cast + direction + null placement on a single key
from "Products"
order by UnitsInStock as long desc nulls last
```
<br/>

```sql
// Works with method expressions
from "Employees"
order by id() as string nulls last
```
<br/>

```sql
// Works with spatial sorting
from "Employees"
order by spatial.distance(Address.Location, spatial.point(0, 0)) nulls first
```
<br/>

```sql
// Per-clause control on a multi-key sort.
// Each clause sets its own null placement.
from "Products"
order by Name nulls first,
         UnitsInStock desc, // omitted: uses default
         PricePerUnit as double nulls last
```
<br/>
    
<Admonition type="info" title="">
    
* If `nulls first` / `nulls last` is Not specified, RavenDB uses the configured default behavior.  
  See [Indexing.Querying.Corax.NullsSortMode](../../server/configuration/indexing-configuration.mdx#indexingqueryingcoraxnullssortmode).      

* The `nulls first` / `nulls last` clause is supported only by the [Corax](../../indexes/search-engine/corax.mdx) search engine.  
  Issuing a query that contains this clause against a Lucene index will return an `InvalidQueryException`.
    
</Admonition>

## `select`

Use `select` to have the query return a projection instead of the full document.  
Learn more in this [projection](../../indexes/querying/projections.mdx) article.

---

## `load`

Use `load` when you need to use data from a related document in a projection or in a [`filter`](../../querying/rql/what-is-rql.mdx#filter) condition.  
See an example in this [projection](../../indexes/querying/projections.mdx#example-viii---projection-using-a-loaded-document) article,
and in [Filter by a related document](../../querying/filtering-query-results/exploration-queries.mdx#filter-by-a-related-document).

---

## `limit`

Use `limit` to limit the number of results returned by the query.  
Specify the number of items to **skip** from the beginning of the result set and the number of items to **take** (return).  
This is useful when [paging](../../indexes/querying/paging.mdx) results.

For document queries on a non-sharded database that use `filter`, the offset skips candidate results **before** filtering,
while the page size limits the number of matching results returned.
See [Filter and paging](../../querying/filtering-query-results/exploration-queries.mdx#filter-and-paging).

```sql
// Available syntax options:
// =========================

from "Products" limit 5, 10       // skip 5, take 10

from "Products" limit 10 offset 5 // skip 5, take 10

from "Products" offset 5          // skip 5, take all the rest
```

## `update`

To patch documents on the server-side, use `update` with the desired JavaScript that will be applied to any document matching the query criteria.  
For more information, please refer to this [patching](../../documents/patching-documents/patch-multiple-documents/client-api.mdx) article.

#### Single-line comments  

Single-line comments start with `//` and end at the end of that line.

```sql
// This is a single-line comment.
from "Companies" 
where Name = "The Big Cheese" OR Name = "Richter Supermarkt"
```
<br/>

```sql
from "Companies"
where Name = "The Big Cheese" // OR Name = "Richter Supermarkt"
```

</ContentFrame>

<ContentFrame>

#### Multiline comments

Multiline comments start with `/*` and end with `*/`.

```sql
/*
This is a multiline comment.
Any text here will be ignored.
*/
from "Companies"
where Name = "The Big Cheese" OR Name = "Richter Supermarkt"
```
<br/>

```sql
from "Companies"
where Name = "The Big Cheese" /* this part is a comment */ OR Name = "Richter Supermarkt"
```
